# gatekeep-pr: separated contexts, reviewed fix wave, CI polling, permission-derived menus

**Goal:** Make `/skill:gatekeep-pr` safe to run on a real PR by default - helpers in fresh contexts, no orchestrator edits, a reviewer before every push, CI read after the push, conflict and permission facts owned by the digest - with the smallest text change per ticket row, inside `skills/gatekeep-pr/` only, and with a before/after control run on past PRs so the first-pass report does not regress.

Ticket: acme/widgets#57. Amends (does not supersede) `doc/specs/2026-10-01-gatekeep-pr-capability-gate-compact-report.md` (fix wave, re-entry, menu overlays) and `doc/specs/2026-09-06-gh-14-gatekeep-ci-evidence-default.md` (Evidence resolution table); both stay live for every clause this spec does not name.

## Problem

The skill today ([`skills/gatekeep-pr/`](../../skills/gatekeep-pr/)) runs Verify and Review inline by default (`reference/assessment.md` "Inline first; dispatch when pi-cohort is present"), so the orchestrator's context holds the verification transcript and the review, and on Claude Code - where the persona files do not exist (`.claude-plugin/marketplace.json` ships `agents: []`, asserted by `scripts/ci.mjs`) - it always runs inline. A `fix` pick applies up to two payloads by orchestrator edits (`reference/post-selection-loop.md` "### Fix wave": "At two payloads or fewer, apply inline"), runs the full verification command once, and pushes with no reviewer between the edit and the push. After the push the skill never reads CI; a first-pass head whose only run is `action_required` is reported as Failed CI (`verification-brief.md` Evidence resolution). The loop never checks `mergeable` before committing or pushing (only the merge precondition does). Menu availability is derived from `isCrossRepository` alone, and `verification-brief.md` L36 reads `viewerPermission` from the REST repo endpoint, which does not carry that field (live probe: empty; REST has `.permissions`, GraphQL has `viewerPermission`). The reported incident (seven files edited by the orchestrator, committed and pushed to a contributor's fork, tag push rejected) follows from those four gaps.

Premise corrections carried from the ticket: the menu grammar is `(not available: <reason>)`, not `- unavailable:`; the headings `### Merge`, `## Re-entry`, `## Inline first` do not exist in that form; no re-review rule exists anywhere in the skill; `gatekeep-pr` is already in `marketplace.json`; the approve endpoint is `POST` (`gh api --method POST ...`).

## Acceptance criteria

Ticket acme/widgets#57, "Acceptance criteria" (Phase 1-7 headings), rows verbatim:

Phase 1 - context separation on the first pass

- [ ] With a helper facility present, step 3 (Verify) and step 4 (Review) are dispatched as two fresh helpers in the same parallel call, `cwd` the PR worktree, each with an absolute `$TMPDIR` output path; the orchestrator reads back only the verifier output schema (`source`, `head_sha`, `checks`/`runs`, one disposition per material claim) and the reviewer's findings report, and raw command output or repro transcripts appear in the rendered report only as a path under `show evidence`. `SKILL.md` "## Steps" and `reference/assessment.md` state this as the default; inline is named as the fallback for a harness with no helper facility only.
  deviates: Verify and Review stay sequential (the shared-worktree contract already in `assessment.md`, "dispatched sequentially - never `worktree: true`"); everything else in the row - fresh helpers by default, `cwd` the PR worktree, absolute `$TMPDIR` output paths, orchestrator reads only the two output contracts, raw output only as a `show evidence` path - is in scope as Design D1. The inline fallback is removed, not named: a harness without a helper facility is out of the skill's support (D7).
- [ ] A repo whose verification command rewrites tracked files declares `serial verify: true` under `## PR gate`; only then do Verify and Review run sequentially, and the hazard sentence (the verifier's local run writes into the worktree the reviewer reads) sits next to the rule in `reference/assessment.md`.
  deviates: no `serial verify` key; sequential is the only mode (D1), so the hazard it would guard does not arise and no sentence documents it.

Phase 2 - fix wave through the hotfix core

- [ ] A `fix` pick never results in the orchestrator editing a tracked file: every payload, including a single one-line payload, is applied by a fresh implementer (PR worktree as `cwd`) given the finding's evidence pack and scoped test commands; payloads are applied sequentially in the one PR worktree; "at two payloads or fewer, apply inline" is removed from `post-selection-loop.md` "### Fix wave".
  in-scope (D2)
- [ ] During the wave no full verification command runs: the implementer's task names only scoped test commands (the test it writes, the test file it touches), and its status report carries the scoped test's failing run before the fix and passing run after it; the verification command appears in `post-selection-loop.md` only in the end-of-wave evidence step.
  in-scope (D2); the end-of-wave evidence step is the CI poll of D4, with the local run as its fallback, so the command's one mention is in `reference/fix-wave.md`, which `post-selection-loop.md` cites.
- [ ] Before any push, a fresh reviewer runs over the wave diff (`<pre-wave HEAD>..HEAD`) and the wave pushes only on a report with no Critical or Moderate finding; otherwise the implementer is re-dispatched with the report verbatim, up to `closureReview.maxFixRounds` rounds (default 3, the same cap the implement phase's remediation loop uses), and when the cap is reached the menu re-renders with the commits unpushed and the reviewer's report summarized.
  in-scope (D3)
- [ ] After the push and after CI evidence resolves (Phase 3), a separate fresh re-review runs with the pre-wave findings list under `## Previous review report (re-review trigger)` and the wave diff under `## Fix delta`; each pre-wave finding is marked resolved or still open from that report before the menu renders, and no finding is marked resolved any other way.
  deviates: no third context after the push. The pre-push reviewer of D3 receives the pre-wave findings list and the wave diff under those two markers and emits one `resolved` / `open` line per pre-wave finding; the orchestrator marks findings only from those lines. Reviewing before the push is what prevents the incident; a second identical review after the push would see the same diff.
- [ ] The hotfix path and the fix wave cite one orchestration section (implementer dispatch, scoped tests, pre-push reviewer gate, re-dispatch cap) by one path and heading; the steps are written in exactly one file and the other file holds only the citation plus its own deltas (worktree, push target).
  deviates: user decision - `skills/chase-bug/hotfix.md` is untouched; the fix wave is written in `skills/gatekeep-pr/reference/fix-wave.md` and the two texts stay duplicated. Hotfix's cap (one round), worktree binding, and squash landing differ from the wave, and a shared section would carry two parameter sets on day one; de-duplication is a follow-up ticket.

Phase 3 - CI as evidence, local run as last resort

- [ ] After a wave's push, the skill polls the pushed head's checks until every resolved check is terminal or `## PR gate` `timeout minutes` (existing key, default 15) elapses; `success` on all satisfies the evidence row with no local run; a blocking conclusion (`failure`, `timed_out`, `error`) re-enters the wave with the failing check named; `neutral`/`skipped`/`cancelled`/`stale` keep today's inert semantics; a run in `action_required` is approved via the forge API when the gate holder has the permission (`gh api repos/{owner}/{repo}/actions/runs/{id}/approve` or the overrides' equivalent) and then polled.
  deviates: approval of a held run is a forge mutation, so it is a menu row (`approve workflow run`, D4) picked by the user, never automatic; everything else in the row - polling after the push, terminal predicates, blocking conclusions re-entering the wave with the check named, inert set unchanged - is in scope as D4. "Re-enters the wave" means the menu re-renders with the failing check in the evidence block and `fix` recommended; no edit happens without a pick.
- [ ] A check still pending when `timeout minutes` elapses stays blocking evidence: the menu renders `wait` (poll another `timeout minutes`) and `stop`, never an automatic local run.
  in-scope (D4)
- [ ] A local full run happens only when no check has appeared on the pushed head within `timeout minutes`, or a held run cannot be approved by this gate holder, or the repo declares `local verification: always`; the evidence record names which of the three triggered it.
  in-scope (D4); "cannot be approved" reads as: the `approve workflow run` row is not available to this actor, or it was picked and the API returned 403/404.
- [ ] On the first pass, a head whose only run is `action_required` is approved (when permitted) and polled like a pushed head; the Fallback (local) row fires only on the same three triggers; `verification-brief.md` "## Evidence resolution" carries both the first-pass change and a fix-wave row, and "### Fix wave" cites that row instead of its own run-the-command sentence.
  deviates: first-pass approval is the same menu row, not automatic (consent rule, `SKILL.md` L11). In scope: `action_required` as the head's only conclusion reads as Pending (not Failed CI), the Pending row names the `approve workflow run` menu row, the Fallback row fires on the three triggers only, Evidence resolution gains a fix-wave row, and `### Fix wave` cites it (D4).

Phase 4 - conflicts and behind-base branches

- [ ] Before the first wave commit, and again before push, the loop checks `mergeable` and whether the branch is behind its base; `CONFLICTING` or behind renders a conflict menu instead of proceeding, and the orchestrator resolving a conflict itself is a listed red flag with an owner section.
  deviates: the conflict check is local (`git merge-tree` against the freshly fetched base, D5), not the remote `mergeable` field, because the remote stays `CONFLICTING` until the local resolution is pushed. Behind-base is not a conflict-menu trigger: it is read once as `mergeStateStatus` and, when `BEHIND` at the merge precondition, renders the `update branch` row (D5). The two check points, the conflict menu, and the red flag are in scope (D5).
- [ ] The conflict menu offers only rows the gate holder can execute now, each with its precondition stated in the row: update the branch via the forge (`gh pr update-branch`, `--rebase` when the forge allows) - only before any wave commit exists and when the forge reports the branch updatable; rebase onto base and `git push --force-with-lease` - only when the PR is in the gate holder's own repo and the gate holder is the PR author; merge base into the branch and resolve conflicts through the Phase 2 implementer-plus-reviewer path - only when the branch is pushable by this actor; post a conflict comment requesting changes - only when the actor can comment; `stop` always.
  deviates: no force-push row (a rewritten head invalidates the comment ledger's SHA chain and every reviewer's anchor; the merge-base row reaches the same end without it). The menu is `update branch` (forge, `viewerCanUpdateBranch` true and no wave commit), `merge base` (implementer merges the base and resolves conflicts through D2/D3, head pushable), `reply` (today's verb, conflict text drafted), `stop`. Rows carry their precondition (D5).
- [ ] After a forge-side update the PR worktree is fetched and fast-forwarded to the new PR head before the wave continues; a worktree holding unpushed wave commits never takes the forge-update row (the merge-base row is the path), so no wave commit is ever discarded by a sync.
  in-scope (D5)

Phase 5 - menus render only possible rows

- [ ] Step 1's digest records the actor's effective permissions, not fork metadata alone: for the base repo, the viewer's permission level and the base branch's protection as far as the actor can read it; for the head, `isCrossRepository`, `maintainerCanModify`, and whether the actor can push to the head branch; whether the repo has workflows triggered by the PR's event; and whether the actor can comment. `fix`, `push`, `merge`, `rebase + force-with-lease`, `update branch`, `suggest`, and the comment row derive availability from those fields; an unreadable permission fails closed (row omitted).
  deviates: digest gains `viewer_permission` (GraphQL `repository.viewerPermission`, replacing the broken REST read), `is_cross_repository`, `maintainer_can_modify`, `merge_state_status`, `can_update_branch` (`viewerCanUpdateBranch`), and - after provisioning, in step 2 - `head_pushable`; base-branch protection, workflow presence, and can-comment are not recorded - protection surfaces through `mergeStateStatus` at the merge precondition, workflow presence through the poll's "no check appeared" trigger, and commenting fails at the write with the forge's error, which the existing `reply` failure path reports. `fix`, `push`, `merge`, `update branch`, `approve workflow run` derive from the recorded fields; unreadable fails closed (D6). `rebase + force-with-lease` and `suggest` do not exist (rows above and below).
- [ ] For a PR whose head the actor cannot push, the menu offers `suggest` instead of `fix`: hunks that only change or delete lines present in the PR's own diff are delivered as review suggestion blocks via the forge's review-comment API, one per hunk; any other hunk (new file, lines outside the PR diff) is delivered as a fenced `diff` block in a single PR comment body, linked from a gist when the body would exceed the forge's comment size limit; the row names which delivery will be used before the pick.
  deferred: follow-up ticket "gatekeep-pr: `suggest` delivery for non-pushable heads". A new verb with two delivery APIs, a gist path with its own authorization, and an unverified 65536-character limit is not a minimal change; the skill operates without it - on a non-pushable head `fix` applies locally to the `pr-<N>` worktree and `push` is omitted with the hint naming the missing permission (today's fork path, D6).
- [ ] No menu row anywhere in the skill renders with a `- unavailable:` suffix: a row the actor cannot execute is omitted, and the hint line names what would have enabled it. On a harness with no helper facility, `fix` and the conflict menu's merge-and-resolve row are omitted for the same reason.
  in-scope (D6), read as: no row renders with the skill's `(not available: <reason>)` suffix; `merge` withheld on a verdict keeps its reason in the `## Verdict` line (`report.md`), not in a row. The no-helper clause has no runtime: a harness without a helper facility is unsupported (D7).

Phase 6 - harness portability

- [ ] Every dispatch sentence in `skills/gatekeep-pr/**` and `skills/chase-bug/hotfix.md` uses harness-neutral wording ("fresh helper via the harness's native facility; persona when available, otherwise the persona's brief inlined in the task text"); the names `pi-cohort` and `subagent()` appear only inside a paragraph headed `Harness notes` in each file.
  deviates: `skills/gatekeep-pr/**` only (hotfix.md untouched, row above). Dispatch sentences name "a fresh helper"; the one paragraph `Harness notes` in `SKILL.md` carries the two harness forms (`subagent()` with the persona on pi; the harness `Agent` tool with the duty text as the prompt on Claude Code). Other files in the skill name neither (D7).
- [ ] On a harness with helpers but no personas (Claude Code), the fix wave still separates implementer, pre-push reviewer, post-push re-reviewer, and orchestrator into distinct fresh contexts; the inline-plus-self-review fallback is removed from both files (Phase 5's omitted rows replace it).
  deviates: three contexts, not four - no post-push re-reviewer (Phase 2 row above). Implementer, pre-push reviewer, and orchestrator are distinct fresh contexts on both harnesses; the inline fallback is removed from `assessment.md` and `post-selection-loop.md` (D7).
- [ ] `gatekeep-pr` is listed in `.claude-plugin/marketplace.json` and `npm test` passes (skill lint, stage-skill lint, marketplace assertions).
  in-scope; already listed, `npm test` is the gate (Tests).
- [ ] A consumer repo whose `.claude/settings.json` holds only the plugin registration and enablement entries (`extraKnownMarketplaces` + `enabledPlugins` for `gauntlet@pi-gauntlet`, the two keys the README's "Use from Claude Code" section already asks for) runs every step of the skill, fix wave and conflict menu included, on Claude Code: no agent files, permission rules, hooks, or overrides keys are added to the repo for it. The persona briefs the fix wave needs (implementer, reviewer) travel with the plugin - inlined in the dispatch task text or shipped by the plugin itself - never copied into the consumer repo.
  in-scope (D7): duty text is inlined in the `Agent` prompt from the skill's own files; nothing lands in the consumer repo.

Phase 7 - authoring shape

- [ ] The edit follows `/skill:forge-skill` "## Authoring rules" (imperative voice; at most two branches per step, each on an observable runtime fact; minimal diff; no provider or model names) and "## Conventions"; `wc -l skills/gatekeep-pr/SKILL.md` stays under 500 and the skill-lint in `npm test` passes.
  in-scope; the static oracle's stricter `< 120` lines for `SKILL.md` stays.
- [ ] Each concern - gather/verify/review briefs, fix wave and hotfix core, CI evidence and polling, conflict menu, permission digest and menu availability, suggest delivery - lives in its own markdown file beside `SKILL.md` (sibling or `reference/<topic>.md`, per forge-skill's file-layout convention); `SKILL.md` keeps the step table and a one-line "read X now" pointer per step, and no step's pointer names more than two files, so a run loads only the file for the step it is in.
  deviates: no re-layout of existing files. One new file, `reference/fix-wave.md`, holds the fix wave, the CI poll, and the conflict menu (the three run in one sequence after a `fix` pick); permissions extend the existing digest in `verification-brief.md` Section A and the overlays in `decision-menu.md`. The step table's pointers already name at most two files; the `fix` verb's pointer in `post-selection-loop.md` names one.

## Design

Plus `scripts/gatekeep-comment-reconcile.test.mjs` (static oracle), `README.md`, `doc/configuration.md`, `CHANGELOG.md`. Untouched: `skills/chase-bug/**`, `agents/**`, `.claude-plugin/marketplace.json`, `scripts/ci.mjs`, `review-baseline.md`.

Live sentences this design replaces (each named here so none stays stale): `verification-brief.md` L4-6 "run the whole thing inline yourself, or hand a section whole to a subagent" -> "Sections B and C are each a fresh helper's whole duty; Section A stays with the orchestrator" (D1); `assessment.md` L61 and Section C "native output format, never overridden at call time" -> "native format, plus the closure lines D3 appends" (D3); `SKILL.md` L31 and `post-selection-loop.md` intro/"### Re-render" lead "re-run step 3's claim check and the review after an own push" and "without a second verification pass - the wave's single pass already covered this head" -> the own-push sequence of D4; Re-render step 4 "inline first; optionally dispatch code-reviewer ... falling back inline" -> "a fresh reviewer helper over the eligible comment deltas" (D7).

### D1 - Verify and Review as fresh helpers, sequential

`SKILL.md` "## Steps" lead sentence becomes: Verify (step 3) and Review (step 4) each run as a fresh helper with `cwd` the PR worktree, Verify first, Review after Verify's output file exists. `assessment.md`'s section "Inline first; dispatch when pi-cohort is present" is renamed "Helpers" and its table keeps rows 3 and 4 (Gather stays with the orchestrator - it owns `gh` reads and the digest); the sentences "inline path is primary", "optimization, never a dependency", and the failure rule "re-dispatch once then inline" are removed. Each helper's task names an absolute output path minted by the orchestrator with `mktemp` under `${TMPDIR:-/tmp}` (two files: `gatekeep-verify.XXXXXX`, `gatekeep-review.XXXXXX`, deleted at Teardown). The Verify helper owns `verification-brief.md` Section B and writes the existing Verifier output schema to its file; `runs[].raw_tail` stays in the file and never in the orchestrator's read - the orchestrator reads `source`, `head_sha`, `checks`/`runs` status and conclusion, and the per-claim dispositions. The Review helper owns Section C and writes the findings report (verdict line, Critical/Moderate/Minor). The orchestrator's readback from the Verify file is the projection: `source`, `head_sha`, `worktree_root`, `run_cwd`, `checks[]` (`name`, `status`, `conclusion`, `url`), `runs[]` (`command`, `result`, `exit_code`, `log_path`), one disposition per material claim; `raw_tail` is replaced by `log_path` (a file under the same `$TMPDIR` dir). `report.md` "show evidence" renders `show evidence: <log_path>` lines instead of fenced captured tails. A helper that leaves its output file empty or outside its section's output schema (the orchestrator mints the file with `mktemp`, so "no file" reads as "empty file"), returns a non-zero result, or (on pi) returns an async handle stops the step with the failure quoted; no inline retry.

### D2 - Fix wave: fresh implementer per payload, scoped tests only

New `reference/fix-wave.md`, section "## Wave". `post-selection-loop.md` "### Fix wave" shrinks to: payload selection (unchanged first paragraph) and "Apply per `reference/fix-wave.md`". Wave: record `pre_wave_head = HEAD`. For each payload in review order, one fresh implementer helper with `cwd` the PR worktree and a task holding the finding's evidence pack (`findings.md` "## Drafted payloads" shape), the scoped test commands (the test it writes or the test file the payload touches; never the `verification command`), and the instruction to commit on the PR branch with one commit per payload. The implementer commits only when its scoped test passes; otherwise it discards its own edits (`git checkout -- <its files>`, removing files it created) and returns `open - <why>`. Its status report carries the scoped test's failing run before the edit and passing run after; a doc-only payload with no test carries `no scoped test` and its diff, and the D3 reviewer is its only gate. The orchestrator edits no tracked file and runs no git write; after each helper it checks `git -C <worktree> status --porcelain` and `HEAD`: on a `done` return, exactly one new commit and a clean tree; on an `open` return, no new commit and a clean tree. Any other state (staged, unstaged, or untracked residue; HEAD moved on `open`) stops the round - no further implementer, menu re-renders naming the files and the payload. An `open` payload is never pushed as fixed, whatever the reviewer reports. Rounds: a round is one pass over the open payloads plus one D3 review.

### D3 - Pre-push reviewer, cap, finding closure

`fix-wave.md` "## Review before push". After the round's payloads, one fresh reviewer helper, `cwd` the PR worktree, read-only, over `<pushed_head>..HEAD` where `pushed_head` is the digest's `headRefOid` (the remote head), so commits a previous round left unpushed are always inside the reviewed range; `pre_wave_head` serves only the empty-round test; its task carries the pre-wave findings list, numbered with this skill's finding ids, under `## Previous review report (re-review trigger)` and `git diff <pre_wave_head> HEAD` under `## Fix delta` (the markers the `code-reviewer` persona already keys on; a `TRAJECTORY:` line it emits is ignored), and asks for its native report followed by one closure line per pre-wave finding: `<finding id>: resolved` or `<finding id>: open - <why>`. `assessment.md` L61 and Section C's "never reshaped at call time" sentences are amended to allow these appended lines; the Claude Code reviewer duty text carries the same closure contract. Push proceeds only when the report has no Critical or Moderate finding; otherwise the implementers are re-dispatched with the report verbatim for the `open` payloads and new Critical/Moderate findings, one round each, up to the cap. Cap: `closureReview.maxFixRounds` via `gauntlet_setting({ key: "closureReview" })` when the tool exists, else 3; `0` means no implementer dispatch - `fix` is omitted and the hint says so. At the cap: commits stay unpushed on the PR branch in the worktree, the menu re-renders with the reviewer's report summarized (verdict line plus Critical/Moderate titles) and `push` omitted with hint "reviewer blocked the wave"; the round count is per run, so `fix` is also omitted, named `fix (round cap reached)`. `push` is available only while the last pre-push review had no Critical or Moderate finding. A re-dispatched implementer receives the reviewer's finding text as the payload for a finding that has no drafted payload. When the pre-push `merge base` reviewer reports Critical or Moderate, the commits stay unpushed and `push` is omitted as `push (reviewer blocked the wave)`. Findings are marked resolved only from the reviewer's `resolved` lines; the orchestrator never marks one. Closure lines are accepted anywhere after the reviewer's findings list (the persona may place its footer lines last). A round in which every payload returned `open` leaves HEAD at `pre_wave_head`: skip the review and the push and re-render the menu with the `open` reasons.

### D4 - CI poll after push; `action_required` as Pending

`fix-wave.md` "## Evidence after push". The push goes to the destination recorded in D6 (`git -C <worktree> push --no-follow-tags <head-url> HEAD:refs/heads/<headRefName>`). After it, poll `gh pr view <n> --json headRefOid,statusCheckRollup` and `gh run list --commit <head> --json databaseId,status,conclusion` every 30 seconds (the Wait course's cadence) for up to `timeout minutes`, on the pushed head only (a moved head stops the poll and takes the existing head-move rule). Normalize first: a `CheckRun` is terminal at `status: COMPLETED` with its `conclusion`; a legacy `StatusContext` maps `state` `SUCCESS`->success, `FAILURE`/`ERROR`->blocking, `PENDING`/`EXPECTED`->pending; the existing `ci checks` filter and reviewer-check exception apply before the predicate. One evidence table, used on the first pass and after a push, in precedence order: (1) any blocking conclusion (`FAILURE`, `TIMED_OUT`, `ERROR`) -> Failed CI, evidence names the check, menu re-renders; `fix` is recommended only when a drafted payload exists for that failure, else the existing dispositions, `wait`, `stop`; (2) a held Actions run (`ACTION_REQUIRED` in the rollup, or `gh run list` showing `action_required` with no rollup entry) -> Pending with the `approve workflow run` row when `viewer_permission` is `WRITE`/`MAINTAIN`/`ADMIN`; when the row is not available, or it was picked and returned 403/404, trigger 2 fires at once; (3) anything pending at `timeout minutes` -> Pending: the `verification evidence pending` overlay (D6) puts `wait` as row 1 (`[recommended]` when `Blockers` is empty, another `timeout minutes`) and omits `merge` as `merge (verification evidence pending)`, consent rows otherwise unchanged, no local run; the Wait course polls `statusCheckRollup` while any check in the resolved set is pending, required or not; when a re-resolve moves the evidence from `source: pending` to CI-sufficient (after a `wait` or an approved held run), the orchestrator dispatches a fresh Section B helper in claim-check-only mode (no local run) so every material claim gets a disposition, and the merge preconditions require a disposition for every material claim - dispositions recorded before an own push carry to the pushed SHA (the own-push sequence runs no claim re-check), while `source: pending` evidence that never had a claim check withholds `merge`; the claim-check-only helper emits the resolved row's `source: ci` block (`head_sha`, `checks`), no run, and the claims; the same claim-check-only dispatch fires inside `## Evidence after push` when an approved held run or a `wait` moves the pushed head from `pending` to CI-sufficient; a held `action_required` rollup CheckRun matches the `actions_runs` entry whose `databaseId` equals the run id parsed from the CheckRun's `detailsUrl`, and the fresh Section B helper dispatched after a 403/404 receives the resolved row (`held run not approvable`) from the orchestrator; (4) at least one success and no blocking or pending -> CI-sufficient, no local run; (5) no success at all - no checks, or only inert `NEUTRAL`/`SKIPPED`/`CANCELLED`/`STALE`/`STARTUP_FAILURE` - after `timeout minutes` -> trigger 1. Local run triggers, exactly three, recorded in the evidence block as `local run: <no conclusive check | held run not approvable | local verification: always>`; the user's existing "CI infrastructure broken" disposition is a pick, not a trigger, and stays as today. `approve workflow run` is `gh api --method POST repos/<base-owner>/<base-repo>/actions/runs/<id>/approve`, then re-poll. `verification-brief.md` "## Evidence resolution" becomes this table (replacing the BLOCK list placement of `action_required`, the Fallback row's condition, and adding the "after a push" sentence that cites `reference/fix-wave.md`).

Own-push sequence (replaces `SKILL.md` L31 and the Re-render lead): push -> this poll -> comment refetch and ledger reconciliation (Re-render steps 1-3, 5 unchanged) -> any eligible source-backed comment delta goes to a fresh reviewer helper (Re-render step 4) -> menu renders from the pre-push reviewer's closure lines for the exact pushed SHA. No claim re-check and no whole-wave review run after an own push; the static oracle's `own push ... re-enters step 4` assertion is rewritten to match this sentence. The red flag "A second verification pass or a second push inside one fix wave" (`SKILL.md`) becomes "A local verification run while CI is pending, or a second push inside one round".

### D5 - Conflict check and menu

`fix-wave.md` "## Conflicts". Before the first wave commit and again before the push, the orchestrator runs `git -C <worktree> fetch origin <base>` then `git -C <worktree> merge-tree --write-tree origin/<base> HEAD` (read-only; exit 0 = clean, exit 1 = conflict; any other exit is an error: report it verbatim and re-render the menu without `fix`). This local check is used instead of the remote `mergeable` field so that a locally resolved conflict is recognized before it is pushed; `gh pr view --json mergeable` stays where it is today (merge precondition). Conflict -> the conflict menu replaces the step: `update branch` (`gh pr update-branch <n>`; precondition in the row: no wave commit exists and `can_update_branch` is true; after it, `git -C <worktree> fetch origin refs/pull/<n>/head && git -C <worktree> merge --ff-only FETCH_HEAD`, then the head-move rule refreshes digest and ledger), `merge base` (one fresh implementer merges the just-fetched `origin/<base>` into the branch and resolves conflicts in one commit, then D3 reviews that commit; precondition: `head_pushable`), `reply` (today's verb, draft text "conflicts with <base>, please update"), `stop`. Rows the preconditions exclude are omitted with the hint. A worktree with unpushed wave commits never shows `update branch`. Separately, at the merge precondition, `merge_state_status: BEHIND` renders `update branch` (same row, same precondition) beside the existing rows, with the verdict withhold reason `behind base` (`report.md` `## Verdict`). Red flag added to `SKILL.md`: "The orchestrator resolving a merge conflict itself" with owner `reference/fix-wave.md` Conflicts. The existing red flag "A code or doc edit sitting in the worktree when a menu renders" gains the scoped exception "except helper residue that `reference/fix-wave.md` `## Wave` names in the re-rendered menu", so the residue-stop rule and the red flag do not contradict. `pre_wave_head` is recorded before the first Conflicts check; a `merge base` commit joins the round's single review, with `git show --remerge-diff <merge-sha>` under `## Fix delta` for that commit instead of the range diff, and consumes no extra round; the round's `## Fix delta` for such a round is `git diff <pushed_head> <merge-sha>^1`, then `git show --remerge-diff <merge-sha>`, then `git diff <merge-sha> HEAD`, so earlier unpushed commits stay inside the reviewed range. A `merge base` picked at the pre-push conflict check (the review already ran) gets one fresh reviewer over `git show --remerge-diff <merge-sha>` alone, gating the push as D3 does, with no extra round counted. A `merge-tree` error at the pre-push check also withholds `push`; the commits stay unpushed.

## Errors and edge cases

- Helper dispatch fails or returns no file: step reports the quoted failure and offers `stop`; no inline fallback. Async handle on pi: stop and report.
- `gauntlet_setting` absent: cap 3. Cap `0`: `fix` omitted, hint "maxFixRounds is 0".
- Fork head not pushable: implementers commit locally; `push` omitted with hint naming `<owner>/<repo>:<branch>`; nothing pushed.
- Local `merge-tree` conflict before the wave: `fix` withheld, conflict menu renders. `merge base` picked: the implementer's merge commit goes through D3 like any payload, then the pre-push check passes and `push` is offered.
- `action_required` from a non-Actions check (no `gh run list` match): no approve row; it is a completed check with no success, so it falls to table row 4/5 - CI-sufficient if another check succeeded, else trigger 1 at timeout.
- Held Actions run and `approve workflow run` not available to this actor: trigger 2 fires at once (the AC's wording), evidence block says `held run not approvable`.
- Poll sees the head move (another push): stop polling, head-move rule.
- Pre-push reviewer finds Critical on a wave commit: new blocker, round consumed, `push` withheld.
- Payload fails its scoped test after the implementer's attempt: implementer discards its edits, returns `open`, no second implementer for it in that round.
- Orchestrator finds residue or an unexpected commit after an implementer: round stops, files and payload named in the re-rendered menu; the orchestrator neither commits nor resets.
- `update branch` returns an error (conflict the forge cannot merge, or 403): row result reported, menu re-renders without that row.
- gatekeep run inside a brainstorm flow's verify phase: the phase tracker's lone-implementer guard blocks the dispatch (pre-existing; the error is surfaced as the helper failure above).
