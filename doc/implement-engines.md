# Implement engines

An implement engine turns an approved spec into a verified implementation. The default waves/task engine uses `writing-plans` and `subagent-driven-development`; the experimental loop engine uses `loop-implementation` and an acceptance-criteria ledger. Both enter the same phase guards and closing gates. See [Loop engine operations](configuration.md#loop-engine-operations) for operator choices and ledger details.

## Admission and phase state

Keep the engine artifact in the resolved plan directory as a file with a path-only `**Spec:**` header containing the repo-relative spec path, optionally backticked. `plan_check({ planPath })` resolves that spec before checking the artifact. In [plan-check.ts](../extensions/lib/plan-check.ts), line 1 exactly `# Ledger - loop engine` selects ledger validation; other input follows task-plan validation. A passing parent tool call stamps both artifact and spec paths and SHA-256 hashes.

The implement-start guard in [phase-tracker.ts](../extensions/phase-tracker.ts) is unchanged: in an armed flow with flow guards enforced, `start implement` requires the stamp, both files to exist, and both hashes to match. Skipping the plan phase does not bypass this guard. The loop driver stamps and commits its skeleton before starting implement. Once implement starts, ledger updates do not require repeated stamping; resume checks the current ledger again.

| Instance | Artifact | Execution |
|---|---|---|
| Waves/task engine | Task plan with waves, tasks, spec citations, scoped tests and verification headers | Task implementers and spec/code reviews, tracked by `plan_tracker` |
| Loop engine | `<resolved plan dir>/<spec stem>-ledger.md` | Fresh `loop-implementer` per seed or row iteration; no task tracker or implement-phase reviewers |

A non-file engine artifact is outside this contract. Supporting an engine whose plan cannot be a hashed file requires a phase-state engine field and corresponding admission changes; that field does not exist.

## Task-plan orchestration

A passing task-plan `plan_check` also returns a compact manifest: an absolute plan/spec header and one JSON line per task with its wave, heading, owned files, scoped test commands, and optional mode, leg, and orchestrator instruction. The [configuration reference](configuration.md#phase-tracker) defines its fields and inclusive 32,768-character rejection boundary. Loop ledgers return no manifest.

During implement, the primary holds the manifest, tracker state, skill resources, structured child statuses and verdicts, patch locations, scoped-test and git coordination output, provisioned worktree paths, and compact delegated answers. It does not open the plan, spec, task bodies, source files, or worker reports, including through shell commands. Workers own those reads. Investigation and questions about task content use delegated reads returning a one-paragraph answer and one-line `path:line` evidence, not source excerpts. A file-only result's saved-output pointer does not authorize the primary to open it.

Implementers and reviewers receive `planPath` and the absolute spec path plus `anchor: "### Task <n>:"`, or `anchors` for a wave review or multi-task repair. Workers match the exact number-and-colon heading prefix (`### Task 4:` does not match `### Task 40:`), read through the next line matching `^#{2,3}\s`, and load the selected sections' Spec, Files, Tests, and combined task/leg Rules themselves. Dispatch-supplied `SCOPED_TEST_COMMANDS` remain independent of task Tests metadata. The primary derives its scoped gate from manifest `tests`, retaining one execution and failure boundary per command element; manifest `files`, `leg`, and `mode` drive ownership, routing, and in-place handling.

Verdict-bearing dispatches use chains with per-task `outputMode: "file-only"`, report output paths, and bounded `outputSchema` values. The wave chain retains implementation followed by spec review, with `stopOn` on the implementation step. Other verdicts and delegated reads use one-step chains whose `stopOn` makes structured JSON visible in `## Outputs` without returning report bodies. The primary routes structured statuses and verdicts; workers read previous reports by path for repairs and re-reviews. Missing or invalid structured results go to delegated diagnosis, never report-body recovery in the primary.

A manifest `orchestrator` instruction runs once after its wave's commit and before the next dispatch, using coordination actions only. Requests to change the plan or spec go through delegated amendment preparation and apply, preserving human approval or standing-grant gates; the primary does not edit those documents. An instruction with no permitted coordination action stops the run.

Compaction and resume recover static state with `plan_check({ planPath })` and `plan_tracker({ action: "status" })`. In-flight state comes only from the primary's transcript lines: `wave <w> base <sha>`, `wave <w> task <n> <status|verdict> <value> report <path> patch <path>`, `wave <w> review <k> tree <path>`, and `funded round <k> of <N> for task <n>`. An in-progress wave without its required lines stops with a note naming the missing evidence, rather than reopening reports, guessing integration state, or resetting a repair budget.

## Verification and finish

Complete implement only after full project verification passes. In verify, run full verification before whole-diff code review, then happy path when selected and the separate conformance review against the spec and original prompt. Repairs invalidate verification and require a successful rerun before the next gate. The loop reuses its passing exit run only while the verified HEAD and clean worktree still match. Its checklist is spec AC rows against the ledger, not tracker tasks. Follow the conformance continuation and closure schema in [loop-implementation](../skills/loop-implementation/SKILL.md) and [subagent-driven-development](../skills/subagent-driven-development/SKILL.md).

[Finish](../skills/finishing-a-development-branch/SKILL.md) reads a ledger's `verification:` command where a task plan supplies `**Verification:**`. Its hard verification gate precedes every menu option; its documented clean-commit/no-change skip rule is the only exception. Before landing, read the artifact's path-only Spec header for telemetry sealing, enumerate both the basename-paired task plan and sibling `<spec stem>-ledger.md`, and remove each tracked candidate. The spec and sealed telemetry ship in the squash; the engine artifact is stripped. Finish includes `loop: cut row <n>` and `loop: amend` audit bodies in its amendment digest alongside `amend:` commits.

## Resume and amendments

[Resume reconstruction](../skills/gauntlet-resume/reference/reconstruction.md) recognizes a ledger by line 1 and pairs it using its Spec header, not its basename. After human confirmation and entry checks it arms the flow through brainstorm, starts plan, calls `plan_check`, skips plan with a loop-engine resume reason, and starts implement. Findings stop reconstruction without task-plan repair. Restore base, verification, iterations, cap, attempts, funding and retry allowances without resolving loop settings; render cap, rows, counters, allowances and all decisions. Every ledger restore, including verify/ship, applies the [shared cap boundary](../skills/gauntlet-resume/reference/reconstruction.md#spec-with-ledger) before phase continuation; a missing cap takes the driver's legacy grant stop, never a settings-derived cap. The resume skill's implement-with-line-1-ledger route restores ledger cap and iterations/retry data, then continues at `Before each dispatch`; verify/ship continues at `After the loop` step 1. Never initialize the task tracker or overwrite a restored ledger. A loop spec without an artifact enters the loop driver's entry sequence to create one.

[Amendment aftermath](../skills/brainstorming/reference/amendment-surface.md) recognizes the same ledger discriminant. It reconciles approved dispositions without a plan writer, `plan_check`, or task-tracker lifecycle: cut disposed rows with disposition evidence, preserve requirement-preserving rows, and reopen re-bounded done rows with `reopened by amendment`. Preserve counters and commit spec plus ledger together with the amendment audit body. A drafted AC text correction backed by quoted implementer test, assertion or code evidence in a `BLOCKED`/`NEEDS_CONTEXT` return is an amendment. Ticket rows, row add/remove, reviewer-only or taste objections, problem statement changes and component boundary changes remain redraws. A redraw removes the ledger as it removes a task plan; it always stops for approval.

Planning also decodes the current spec grant before waiting on a baseline failure. Under amend permission, a concrete `Recommendation: narrow <filter>` re-dispatches the plan writer with that filter and reruns baseline; `amend` uses the amendment surface and its aftermath. `fix-first` enters ticket shaping's own write gate, not an automatic unrelated repair. Missing concrete filters, no recommendation and absent or budget-only grants retain the human decision; dirty-source recovery never gains discard permission.

## Stops, models and telemetry

Preserve branch state on a stop and leave implement active. Use the existing [stop-note contract](../skills/subagent-driven-development/stop-note.md): one screen of plain words naming the concrete failing evidence and decision, with retry, approved amendment, or stop choices. The loop driver additionally enforces row allowances, empty-commit stagnation, a row-scaled durable total iteration cap and the one-commit/clean-tree return boundary. The cap is seeded from non-cut row count times the per-row multiplier plus one seed dispatch, stays fixed across cuts and reopening, and is recomputed only on redraw. A clean cap stop also offers the durable `cap +N` grant; see [Loop engine operations](configuration.md#ledger-and-recovery) for its contract. Never silently cut a row or reopen closed rows after failed exit verification.

Both engines decode the current `**Amend-grant:**` before execution continuation. Absent, `none` or budget-only values supply no automatic decision or execution escalation. Malformed grants, unavailable settings or missing resolved `implModel`, dirty-tree/commit-boundary failures, cap, stagnation, funded re-review `STAGNANT`, `REJECT` and redraws retain their stop routes. Amendment permission supplies no review credits, cap extension or extra unnamed retry.

| Site under amend permission | Bounded continuation | Spent identity on resume |
|---|---|---|
| Waves task after two failed execution attempts | One fresh-context implementer on resolved `escalationLoop.implModel`, preserving payload, isolation, prior report and accepted siblings; success still passes scoped tests and SR/CR before commit | Matching task transcript line `escalated round for task <n> after 2 failed attempts` |
| Loop unresolved row at its allowance | One normal loop-implementer dispatch on `implModel`, within cap and existing bump/validation rules; parent records `row <n> escalated \| implModel round \| allowed attempts <attempts + 1>` and commits `loop: escalate row <n>` | Durable row escalation decision |
| Loop exit verification failure | One fresh-context `implementer` repair per flow on `implModel`, one counted iteration within cap, clean tree and exactly one child commit; preserve all rows, mapping, cap and prior decisions, then rerun the failing leg's command once | Parent `loop: repair verification` commit |

Dispatch errors, non-`DONE` returns and validation failures consume the applicable round. Missing or unrecoverable identity means spent; retry, funding and amendments never re-arm it. Loop escalation markers do not reset child-only stagnation. Verification repair never reopens rows or spends another leg's verification or verify-phase credits. These execution rounds are independent of review escalation, convergence exceptions and funded rounds; funded loop attempts keep their ordinary worker model.

Every stop ends in `Recommendation: <option> - <why>` or `Recommendation: none - <why>`. Waves takes a named in-task repair only within the two ordinary attempts, or a named spec/plan amendment through the amendment surface with evidence and audit; loop auto-takes only a named authorized amendment and returns to its ordered checks without a free retry. Repeated whitespace-normalized evidence on the same task/row yields `none`, not another automatic decision. Retry, more attempts, cap increases, consent and redraw wait for the human; `fix-first` enters ticket shaping's own gate. See the [waves execution procedure](../skills/subagent-driven-development/reference/fix-loop.md) and [loop driver](../skills/loop-implementation/SKILL.md) for the exact ordering and recovery contract.

Pin an engine worker through `subagents.agentOverrides.<persona>.model`, for example `subagents.agentOverrides.loop-implementer.model`. The ordinary loop dispatch omits `model:`; grant-authorized escalation passes the resolved `escalationLoop.implModel` instead; its persona leaves model and thinking unset, so an unset override inherits the parent model. A parent phase-model switch is not worker-model isolation without a pin.

The spec records `**Engine:** loop` or `**Engine:** waves` directly below `**Amend-grant:**`; absent means waves. `**Engine:** deferred` (written by gate option 6, the draft-PR handoff) is not a third engine: it means no engine was selected, and finishing and `gauntlet-resume` stop on it until `brainstorming #N` re-gates the spec PR and replaces it with `waves` or `loop`. The telemetry recorder emits `{ kind: "engine", engine: "loop" | "waves" }` on brainstorm completion or skip, including resume. [Telemetry derivation](../extensions/lib/telemetry-record.ts) takes the last engine event, defaulting to waves, and derives iterations from loop-implementer dispatches. `gauntlet-performance` prints both fields; legacy records show waves and empty iterations. The ledger's durable dispatch counter supports recovery; telemetry reports observed persona dispatches.
