# Implement engines

An implement engine turns an approved spec into a verified implementation. The default waves/task engine uses `writing-plans` and `subagent-driven-development`; the experimental loop engine uses `loop-implementation` and an acceptance-criteria ledger. Both enter the same phase guards and closing gates. See [Loop engine operations](configuration.md#loop-engine-operations) for operator choices and ledger details.

## Admission and phase state

Keep the engine artifact in the resolved plan directory as a file with a path-only `**Spec:**` header containing the repo-relative spec path, optionally backticked. `plan_check({ planPath })` resolves that spec before checking the artifact. In [plan-check.ts](../extensions/lib/plan-check.ts), line 1 exactly `# Ledger - loop engine` selects ledger validation; other input follows task-plan validation. A passing parent tool call stamps both artifact and spec paths and SHA-256 hashes.

The implement-start guard in [phase-tracker.ts](../extensions/phase-tracker.ts) is unchanged: in an armed flow with flow guards enforced, `start implement` requires the stamp, both files to exist, and both hashes to match. Skipping the plan phase does not bypass this guard. The loop driver stamps and commits its skeleton before starting implement. Once implement starts, ledger updates do not require repeated stamping; resume checks the current ledger again.

| Instance | Artifact | Execution |
|---|---|---|
| Waves/task engine | Task plan with waves, tasks, spec citations, scoped tests and verification headers | Task implementers and one integrated wave review, tracked by `plan_tracker` |
| Loop engine | `<resolved plan dir>/<spec stem>-ledger.md` | Fresh `loop-implementer` per seed or row iteration; ledger-derived task view via `plan_tracker refresh`, no implement-phase reviewers |

A non-file engine artifact is outside this contract. Supporting an engine whose plan cannot be a hashed file requires a phase-state engine field and corresponding admission changes; that field does not exist.

## Ledger task projection

`plan_tracker refresh` resolves the ledger's Spec reference against its repository root and reads the original indexed acceptance criteria. Single-repo rows use their row number; coordinated rows use the original AC index in `## Leg mapping`. Each row's display label contains the full criterion text, flattened to one line without checkbox markup or disposition metadata. Missing or unreadable specs, missing criteria and empty descriptions reject refresh atomically; row numbers alone never substitute for descriptions.

For allowance ledgers, unresolved rows and done rows with attempts above zero display `<attempts>/<effective allowance>: <description>`. Cut rows, baseline-done rows and legacy cap-only ledgers display only the description. Coordinated labels append the owning repo. Task names stay `row N` or `row N (repo)` for matching and telemetry; `label` is projection-only, absent from the `init`/`add` input schema. The widget shows the label, while status separates identity from display text: `row 3 | 2/5: Verify loop behavior and recovery`.

Handoff copies status verbatim. Resume strips the recognized description suffix before restoring or comparing canonical ledger names, retains legacy plain and numeric-prefix names, and leaves Gn and other names unchanged. Refresh recomputes labels from current spec and ledger bytes; changed descriptions or allowances never create another task. The [brief contract](../skills/gauntlet-resume/reference/brief-contract.md#tracker-output-grammar) owns the parsing grammar.

## Task-plan orchestration

A passing task-plan `plan_check` also returns a compact manifest: an absolute plan/spec header and one JSON line per task with its wave, heading, owned files, scoped test commands, and optional mode, leg, and orchestrator instruction. The [configuration reference](configuration.md#phase-tracker) defines its fields and inclusive 32,768-character rejection boundary. Loop ledgers return no manifest.

During waves implement, the primary holds the manifest, tracker state, skill resources, structured child results, patch locations and coordination output. It delegates plan/spec/task/source reads. It may read a saved worker report directly with `limit: 300` only for unresolved concerns, blocked/context questions or actionable `FIX_FIRST`/`REJECT` findings, at most once per printed report-path observation per wave, without pagination. An oversized report gets one compact wave-reviewer retry (findings and footer, at most 150 lines); a second overflow stops. Report-relay children are forbidden; delegated source-fact lookups remain valid. See [Orchestrator holds](../skills/subagent-driven-development/SKILL.md#orchestrator-holds). This exception changes neither the plan/spec/source boundary nor the loop engine.

Implementers and reviewers receive `planPath` and the absolute spec path plus `anchor: "### Task <n>:"`, or `anchors` for a wave review or multi-task repair. Workers match the exact number-and-colon heading prefix (`### Task 4:` does not match `### Task 40:`), read through the next line matching `^#{2,3}\s`, and load the selected sections' Spec, Files, Tests, and combined task/leg Rules themselves. Dispatch-supplied `SCOPED_TEST_COMMANDS` remain independent of task Tests metadata. The primary derives its scoped gate from manifest `tests`, retaining one execution and failure boundary per command element; manifest `files`, `leg`, and `mode` drive ownership, routing, and in-place handling.

Verdict-bearing dispatches use one-step chains with per-task `outputMode: "file-only"`, report paths, bounded `outputSchema` values and `stopOn` to expose structured JSON. Integrate task patches in plan order, run the wave union of scoped commands, then dispatch exactly one initial `wave-reviewer` over the integrated diff. Anchored reviews combine a spec-clause table with prioritized code findings; unanchored reviews produce findings only. Gate failures go to repair before review. Repairs use the current tree, preserve accepted siblings and prior reports, and pass the same scoped gate before re-review. Minor-only findings ship without a fix round. A missing structured result is first recovered from the task's identity-matched `output.json` capture; if no acceptable capture exists, it goes to read-only diagnosis addressed to `delegate` with `Do not edit any file.` Report-body recovery stays forbidden. A missing or zero-byte initial patch counts as a failed attempt and goes to repair on the current tree, retaining accepted siblings and applying nothing. A nonempty initial patch that fails `git apply --index` hard-stops; it does not trigger an automatic rebuild. [The Wave Loop](../skills/subagent-driven-development/SKILL.md#the-wave-loop) owns snapshots, bounded repairs, escalation and the narrowly triggered rebuild recipe.

A manifest `orchestrator` instruction runs once after its wave's commit and before the next dispatch, using coordination actions only. Requests to change the plan or spec go through delegated amendment preparation and apply, preserving human approval or standing-grant gates; the primary does not edit those documents. An instruction with no permitted coordination action stops the run.

Compaction and resume recover static state with `plan_check({ planPath })` and `plan_tracker({ action: "status" })`. In-flight state comes only from the primary's transcript lines: `wave <w> base <sha>`, `wave <w> task <n> <status|verdict> <value> report <path> patch <path>`, `wave <w> review <k> tree <path>`, and `funded round <k> of <N> for task <n>`. An in-progress wave without its required lines stops with a note naming the missing evidence, rather than reopening reports, guessing integration state, or resetting a repair budget.

## Verification and finish

The waves engine completes implement only after full project verification passes. The loop completes implement through the tracker when every ledger row is closed; verify step 1 runs the [gate set](../skills/loop-implementation/SKILL.md#gate-set): the deduplicated union of (owning checkout, command) pairs from each non-cut done row's first evidence segment, in first-contributing-row order. `## Leg mapping` supplies coordinated ownership; without a mapping, every row runs at home. An all-cut ledger prints `gate set empty - every row cut` and continues. The ledger's `verification:` header records CI's full command, never a local loop gate. A missing `checks:` line stops with `ledger has no checks: line - seeded under the old contract`; stop is the only option, with no migration or full-command fallback.

After seed, [Driver holds](../skills/loop-implementation/SKILL.md#driver-holds) limits implement-phase reads to the ledger, the child's return file, git boundary commands, skill resources and overrides. The driver holds the decoded amendment grant and leg checkout paths from seed or authorized restore, refreshing them during a human-directed amendment outside the loop. It does not read the spec, source, test output or logs to diagnose failures.

Verify mints `LOG_DIR=$(mktemp -d)` once per session and runs gate pairs serially, redirecting stdout and stderr to `$LOG_DIR/gate-<i>.log`. The driver retains only `gate <i> exit <code> <log path>` and stops at the first nonzero exit. The log handoff gives a repair child the failing command, checkout, exit code and log path, never pasted output. Only the verify-step-1 human stop reads the log's last 20 lines (`tail -n 20`).

In verify, run verification before whole-diff code review, then happy path when selected and the separate conformance review against the spec and original prompt. Repairs invalidate verification and require a successful rerun before the next gate: the full command set for waves, the gate set for loop, including every conformance repair and convergence site. The loop's checklist is spec AC rows against the ledger, not tracker tasks; conformance remediation uses normal durable `G<n>:` tasks on the same tracker. Follow the conformance continuation and closure schema in [loop-implementation](../skills/loop-implementation/SKILL.md) and [subagent-driven-development](../skills/subagent-driven-development/SKILL.md).

[Finish](../skills/finishing-a-development-branch/SKILL.md) uses the loop gate set for a ledger and `**Verification:**` for a task plan. Its hard verification gate precedes every menu option; its documented clean-commit/no-change skip rule is the only exception. A loop finish mints its own session log directory and retains the ordered (leg, command) pairs for post-squash reruns in each leg's primary. A fresh-session retry after stripping reconstructs those pairs from the committed pre-strip ledger, never from spec verification contracts. Loop PR bodies end `## Summary` with `Verification: scoped - <commands>; CI on this push holds the full run`. Before landing, read the artifact's path-only Spec header for telemetry sealing, enumerate both the basename-paired task plan and sibling `<spec stem>-ledger.md`, and remove each tracked candidate. The spec and sealed telemetry ship in the squash; the engine artifact is stripped. Finish includes `loop: cut row <n>` and `loop: amend` audit bodies in its amendment digest alongside `amend:` commits.

## Resume and amendments

[Resume reconstruction](../skills/gauntlet-resume/reference/reconstruction.md) recognizes a ledger by line 1 and pairs it using its Spec header, not its basename. After human confirmation and entry checks it arms the flow through brainstorm, starts plan, calls `plan_check`, skips plan with a loop-engine resume reason, and starts implement. Findings stop reconstruction without task-plan repair. Recover pending work before changing headers. Restore base, verification, iterations, attempts, decisions and a present `allowance:` without re-reading loop settings or consuming an approval carrier. Admission requires exactly one `allowance:` or legacy `cap:` header; both or neither stops for human repair. For an admitted cap-only ledger after recovery, resolve the current setting, replace `cap:` with `allowance: <n>`, and commit `loop: migrate allowance`; leave every counter and row cell unchanged. Render the restored allowance, rows, counters and decisions. Each `row <n> retry` decision adds one to that row's effective allowance; its `allowed attempts` tail is audit text only. A `row <n> escalated` decision keeps the row's escalation spent. An unresolved row already at its effective allowance takes the normal stop, never an automatic retry. Implement resumes at `Before each dispatch`; verify/ship continues at `After the loop` step 1. Restore the task view with one ledger-path `plan_tracker refresh` after pending recovery; a verify/ship brief first re-initializes its saved task list so refresh preserves `G<n>:` tasks. Never overwrite a restored ledger. A loop spec without an artifact enters the loop driver's entry sequence to create one.

[Amendment aftermath](../skills/brainstorming/reference/amendment-surface.md) recognizes the same ledger discriminant. It reconciles approved dispositions without a plan writer or `plan_check`: cut disposed rows with disposition evidence, preserve requirement-preserving rows, and reopen re-bounded done rows with `reopened by amendment`. Preserve counters and commit spec plus ledger together with the amendment audit body; the driver's next refresh projects the new statuses. A done row reopened during verify stops with `Stopped: row <n> reopened by amendment during verify`; only an authorized ledger return closes it, with verify still active, followed by a rerun of step 1. A drafted AC text correction backed by quoted implementer test, assertion or code evidence in a `BLOCKED`/`NEEDS_CONTEXT` return is an amendment. Ticket rows, row add/remove, reviewer-only or taste objections, problem statement changes and component boundary changes remain redraws. A redraw removes the ledger as it removes a task plan; it always stops for approval.

During waves implement, delegated `Amend-apply:` performs local maintenance rather than regenerating the plan. Preserve original task identity, wave order, state and evidence; reopen completed tasks only for changed semantic obligations or work, not shifted anchors or meaning-preserving rewording. `**Baseline policy:** implement-local` retains valid historical command evidence at its measured revisions; it does not assert freshness at current HEAD. Run only changed/added commands or missing/invalid evidence on an identified execution tree, recording nonzero executed-test counts. Preserve declared in-flight repairs, including staged source, without committing, restoring or discarding them merely to plan. Match retained failures to command/assertion/path and repair evidence, keeping unrelated regressions blocking. An explicit full refresh runs all commands and restores ordinary uniform evidence. Parent `plan_check`, the integrated wave gate, review and final verification remain mandatory. See [Implement amendments](../skills/subagent-driven-development/reference/implement-amendments.md) and [historical evidence](../skills/writing-plans/reference/plan-contract.md#implement-only-historical-evidence).

Planning also decodes the current spec grant before waiting on a baseline failure. Under amend permission, a concrete `Recommendation: narrow <filter>` re-dispatches the plan writer with that filter and reruns baseline; `amend` uses the amendment surface and its aftermath. `fix-first` enters ticket shaping's own write gate, not an automatic unrelated repair. Missing concrete filters, no recommendation and absent or budget-only grants retain the human decision; dirty-source recovery never gains discard permission.

## Stops, models and telemetry

Preserve branch state on a stop and leave the current phase active: implement for execution stops, verify for verify-step gate failures. Use the existing [stop-note contract](../skills/subagent-driven-development/stop-note.md): one screen of plain words naming the concrete failing evidence and decision, with retry, approved amendment, or stop choices. The loop driver enforces one shared per-row allowance, empty-commit stagnation and the one-commit/clean-tree return boundary. A fresh ledger takes its `allowance:` from the run's `; allowance N` approval suffix or resolved `loopEngine.maxIterationsPerRow` (default 4). `iterations:` counts dispatches for recovery and telemetry; it never stops the run. There is no total iteration cap. Exhausted rows offer `retry <n> | <hint>` (one extra attempt for that row), `rows +N` (increase every row's allowance), amendment or stop; see [Loop engine operations](configuration.md#ledger-and-recovery). Never silently cut a row or reopen closed rows after a failed verify-step gate.

Both engines decode the current `**Amend-grant:**` for automatic amendment decisions. Absent, `none` or budget-only values supply no automatic decision. Both engines' execution escalation is independent of amend permission. Malformed grants, unavailable settings or missing resolved `implModel`, dirty-tree/commit-boundary failures, exhausted row allowance, stagnation, funded re-review `STAGNANT`, `REJECT` and redraws retain their stop routes. Amendment permission supplies no review credits or extra attempts.

| Execution site (no amend permission required) | Bounded continuation | Spent identity on resume |
|---|---|---|
| Waves task after two failed execution attempts (independent of amend permission) | One implementer on resolved `escalationLoop.implModel`, current tree and same payload, with no fresh-context override; success still passes scoped tests and integrated wave review before commit | Matching task transcript line `escalated round for task <n> after 2 failed attempts` |
| Loop row's last allowed attempt (`attempts == effective allowance - 1`), with no prior escalation decision | Normal loop-implementer dispatch on resolved `implModel`, counted within the allowance; record `row <n> escalated \| implModel round \| allowed attempts <effective allowance>`, commit `loop: escalate row <n>` and print `escalated round for row <n>` | Durable row escalation decision; retry, `rows +N` and resume never re-arm it |
| Loop verify-step gate failure | One fresh-context `implementer` repair per flow on `implModel`, no row attempt or allowance change, clean tree and exactly one child commit; preserve all rows, mapping and prior decisions, then rerun the failing checkout's gate pairs once, output to `$LOG_DIR` | Parent `loop: repair verification` commit |

Dispatch errors, non-`DONE` returns and validation failures consume the applicable round. Missing or unrecoverable verification-repair identity means spent; retry and amendments never re-arm it. Only retry starts new stagnation and validation-miss windows; `rows +N` resets neither. Spent row escalation means later authorized attempts use the ordinary worker model. Verification repair never reopens rows or spends another leg's verification or verify-phase credits. Execution escalation is independent of review escalation, convergence exceptions and waves funding.

Every stop ends in `Recommendation: <option> - <why>` or `Recommendation: none - <why>`. Waves takes a named in-task repair only within the two ordinary attempts, or a named spec/plan amendment through the amendment surface with evidence and audit; loop auto-takes only a named authorized amendment and returns to its ordered checks without a free retry. Repeated whitespace-normalized evidence on the same task/row yields `none`, not another automatic decision. Retry hints, allowance increases, consent and redraw wait for the human; `fix-first` enters ticket shaping's own gate. See the [waves execution procedure](../skills/subagent-driven-development/SKILL.md#the-wave-loop) and [loop driver](../skills/loop-implementation/SKILL.md) for the exact ordering and recovery contract.

Pin an engine worker through `subagents.agentOverrides.<persona>.model`, for example `subagents.agentOverrides.loop-implementer.model`. Ordinary loop attempts omit `model:`; the last allowed attempt and exit-verification repair pass the resolved `escalationLoop.implModel` instead. Neither needs amend permission. The loop persona leaves model and thinking unset, so an unset override inherits the parent model. A parent phase-model switch is not worker-model isolation without a pin.

The spec records `**Engine:** loop` or `**Engine:** waves` directly below `**Amend-grant:**`; absent means waves. `**Engine:** deferred` (written by gate option 6, the draft-PR handoff) is not a third engine: it means no engine was selected, and finishing and `gauntlet-resume` stop on it until `brainstorming #N` re-gates the spec PR and replaces it with `waves` or `loop`. The telemetry recorder emits `{ kind: "engine", engine: "loop" | "waves" }` on brainstorm completion or skip, including resume. [Telemetry derivation](../extensions/lib/telemetry-record.ts) takes the last engine event, defaulting to waves, and derives iterations from loop-implementer dispatches. `gauntlet-performance` prints both fields; legacy records show waves and empty iterations. The ledger's durable dispatch counter supports recovery; telemetry reports observed persona dispatches.

## Post-merge evidence recipe

For a ticket requiring first-run evidence, use an approved post-merge loop run in the target repo. Read one sealed record and confirm `derived.engine: loop`, `derived.iterations` equals the observed `loop-implementer` results, and `derived.events_dropped: 0`. From that same record, report implement-phase child dispatches, `derived.plan.tasks - derived.plan.skipped` at implement completion, `derived.verification_runs`, and the `disp/task` ratio printed by `gauntlet-performance`. Do not combine records or substitute ledger iteration counters for observed dispatches. See [telemetry definitions](configuration.md#telemetry).

Before an agent posts a first-run comment, obtain explicit confirmation of its exact text under the project's `## Issue tracker` rules; the requester may post it instead. Documenting this recipe does not authorize a ticket comment.
