# Loop engine: one dispatch may close several rows, seed may stop after one

**Goal:** Let a `loop-implementer` return close the target row plus any same-leg `open` rows it proved in the same session, declared only through the ledger diff and one decision line per changed row, and let seed record evidence for at least one non-cut row instead of all of them with one automatic retry on a seed miss - the parent stays a reader of the return, the tracker needs no change, and the worker owns ordering and the extras pick as prose guidance.

## Problem

A loop run pays one fresh-context dispatch per acceptance-criteria row, and the seed dispatch must write or name a selective check for every non-cut row before any code exists. A twelve-row ticket whose rows share one helper costs twelve sessions that each re-read the spec, the ledger and the diff, and a seed that misses one row's evidence is a human stop with no automatic retry (`skills/loop-implementation/SKILL.md:74,104`). The parent's admission rule enforces this: "Exactly the target row's mutable cells change" (`SKILL.md` "Validate the return"), so a worker that could close row 4 in one line after finishing row 3 is forbidden from doing so.

Premises checked against the current contracts. Corrected: the ticket plans no cluster detection, no upfront grouping, no cluster-wide in-progress state and no extras cap - closure of extras is opportunistic and worker-decided in-session (#110 AC 1, AC 4; `extensions/plan-tracker.ts:103-106` names one pending row). Corrected: the scout's objection that the ticket reintroduces a `check` column and a row-close run reads the displaced Reporter-note history; the body's AC 1 and AC 3 exclude both. Supported: batching does not grow the final review - whole-diff review and conformance run once after the loop however many sessions produced the diff (`SKILL.md:158`); what batching changes is the blast radius of a dead session (one commit per session) and attribution (extras close with attempts unchanged). Supported: the tracker already accepts out-of-order `done` rows (`extensions/plan-tracker.ts:261-267` orders non-pending rows before open rows ahead of the pending-suffix check) and attributes a `done` row to the child only through a `row <n> done | ... | ...` decision line (`plan-tracker.ts:136`), which is why AC 2's per-row line is load-bearing. Unverified: the cost gain rests on eval fixtures, no live multi-row run exists (Open question 1). Implicit dependencies: the pi runtime package is absent in this worktree and the pi-cohort dispatch runtime was not read; neither matters because the dispatch call shape is unchanged. The two new eval fixtures do not exist yet; they are deliverables.

Framing: pivoted to B - extras only after the target closed `done`, one at a time, each check-first, a half-done extra reverted before commit; the user chose B with no count, no setting and no planning artifact. The ordering rule is a worker obligation; the parent validates the return and never polices ordering (cut question on AC 1 / AC 12, answer A).

## Design

The axis settled at approach selection: the "which rows closed" fact lives in the ledger diff and its decision lines (approach 1), not in a commit-body list the parent would have to write back (approach 2) and not in a seed-only change (approach 3). The parent reads; the worker writes.

### Declaration channel (AC 1, AC 2)

The declaration of what a return closed is the set of new decision lines. Admission is set equality: the rows whose cells changed and the rows that gained exactly one new `row <n> <status> | ... | ...` line are the same set, the target's line first. No second declaration exists - no `closed:` body line, no new column, no new grammar - because two statements of one fact would be a thing to disagree. The grammar is unchanged; its slots are named (AC 5): the middle slot is what was done; the third slot is, for `done`, what later rows can build on (a new file, helper, interface or fixture) - `nothing new to build on` when the row added no reusable artifact - and, for `failed`, what the next iteration should not redo or should try differently. Example of a conforming two-row return: row 3 `open -> done`, attempts 1, evidence `node --test test/a.test.mjs; 2 pass`; row 4 `open -> done`, attempts 0, evidence `node --test test/b.test.mjs; 1 pass`; decisions appended `row 3 done | adds helper parseRow in lib/ledger.mjs | parseRow in lib/ledger.mjs parses a ledger row with escaped pipes` then `row 4 done | row 4 reads its cells through parseRow | nothing new to build on`; commit subject `loop: row 3 done`; body unchanged (`pending:` tuple and `iteration:` lines). The next dispatch's `previous decision:` is the target's new line (row 3's), never the last extra's: in the admitted `failed` target plus `done` extra shape the target's line carries the retry guidance.

## Errors and edge cases

- A `done` extra with no new decision line, a decision line for a row whose cells did not change, two new lines for one row, a `failed` extra, an extra from another leg, a changed attempts cell on an extra, a touched `cut`/`done` row, or an empty evidence cell on a changed row: ordinary validation miss. The parent restores every non-target row from the saved copy, sets the target `failed` with `iteration <i>: <miss>` evidence, commits `loop: repair row <n>` - today's repair, unchanged.
- A `failed` target beside an evidenced `done` extra: admitted. The driver does not police ordering.
- Seed with `<k>` below 1, `<k>`/`<m>` not matching the ledger, a `failed` row, a changed attempts cell, or a touched cut row: seed miss. The parent restores every non-cut row, headers and decisions from the saved copy, retains iterations, clears `pending:`, commits `loop: repair seed`, and re-dispatches seed once with the miss in `hint:` inside the existing two-miss window; the retry starts from the restored ledger, so a `failed` row or bumped attempts from the rejected attempt cannot leak into the next before-image. The second consecutive miss is the human stop; a validated seed resets the window so ordinary dispatch starts clean. Seed selection reads the ledger at HEAD: after the repair no `row 0 done` line survives, so `seed` is selected again; a resume between repair and retry re-seeds plainly (the miss text lived only in the transient hint).
- A seed-left `open` row has an empty evidence cell by design; the gate set reads `done` rows only, so it never meets an empty command.
- Stagnation rule 3 is unchanged: a multi-row return changes statuses, so it is progress. Allowance and escalation are untouched: extras never move attempts, so a bad extra spends no allowance; a regression into it surfaces at the verify-step-1 gate set (#109's accepted policy).
- Dirty or multi-commit return: the existing boundary stop, with the restore widened to every row the child changed (target and extras) plus the tuple, in the driver and in resume reconstruction, so an unadmitted `done` extra never projects `complete` before the human's discard/reset decision; code changes, commits and consumed iterations stay preserved. The worker's revert-before-commit rule keeps a half-done extra out of an admitted commit; a dead session loses its unfinished extras with the target, as it loses the target today.
- Companion admission: same set rule per leg; a foreign-leg row is rejected as today; an `open` seed row with empty evidence is admitted; every admitted changed row and decision line reaches the home ledger through the `loop: record` commit; a companion seed miss takes the seed repair and one retry.
- Targeting after a multi-row return: every new line stays durable in `## Decisions` for attribution; the operational decision and the next dispatch's `previous decision:` are the target's new line (a `failed` target's retry guidance is never displaced by an extra's `done` line); durable status beats a decision's suggestion, so the next target resolves from row statuses as today.
