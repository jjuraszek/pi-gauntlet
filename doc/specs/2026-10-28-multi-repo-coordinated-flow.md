# Multi-repo coordinated flow: legs across N repositories

**Goal:** Let one gauntlet run span N repositories as ordered legs - one shared worktree name, one worktree per repo created and torn down under that repo's own overrides and settings, one home spec with a per-leg split and a leg file in every companion, per-leg rule reading (root and nested `AGENTS.md`/`CLAUDE.md`), one brief that resumes every leg from the home, and one ship choice fanned out to every repo - so a two-repo change is handed off, resumed, and shipped as one run instead of N hand-coordinated ones.
**Amend-grant:** every later spec amendment in this flow (corrected facts, paths, verification lines, and scope, acceptance-criteria, or public-contract edits alike) applies without asking; only a redraw (changed problem statement, component added, removed, or re-bounded) still stops for you, and the grant never stands in for a spec approval.
**Engine:** waves

## Problem

Framing: kept - one coordinated run. The user rejected N linked single-repo runs as the current, inefficient practice, and the smaller "rules-only" change as leaving a two-repo run unresumable.

A gauntlet run today is one repository: one worktree, one branch, one spec in that worktree, one plan or ledger, one telemetry record, one brief, one finish. A change that must land in two repositories at once (an API contract in `repo-a` and its consumer in `repo-b`, or a tool and the package that calls it) gets two worktrees in one session, but every downstream stage sees only one of them:

- pi-cohort's `handoff` skill records one run worktree - the one most recently used by later work - and demotes any second to an `Also seen:` open question (cohort `skills/handoff/SKILL.md:28-35`), so the brief's `worktree:` field names one repo and the other leg's state is lost.
- `/skill:gauntlet-resume` entry check 3 compares the session checkout's git common dir with the brief worktree's and stops on a mismatch (`skills/gauntlet-resume/SKILL.md:83-91`, commit `49d1bce1`), so a session in `repo-a`'s primary cannot resume a brief whose worktree is in `repo-b`, and the stop is correct by its rule: there is no multi-repo run for it to recognize.
- The only multi-repo configuration is shape-ticket's `- sibling: <clone url>` lines under `## shape-ticket` in the overrides file, read by its audit scout alone (`skills/shape-ticket/reference/repo-audit.md:11`, `README.md:334`); the scout parses each value with its shared parser (`NAME`, `IDENTITY`, `PATH` = `<PRIMARY parent>/<NAME>`) and reports a missing checkout `not found`, never a stop.
- Rule reading is thin for any N: brainstorming's Project Routing reads `AGENTS.md` by name; `CLAUDE.md` and "touched-area routes" are read only by shape-ticket's scout (`repo-audit.md:42`); nested `AGENTS.md` is a prose mention (`tracker-ladder.md:7`); the implementer, loop-implementer, and reviewer personas read neither (`agents/implementer.md`, `agents/loop-implementer.md`, `agents/code-reviewer.md`); only `agents/plan-writer.md:31` reads the root `AGENTS.md`.
- The finish gate's five options act on one `$WORKTREE`, `$PRIMARY`, `$FEATURE`; the telemetry seal takes one `--worktree` and one `--spec` and runs before the first landing command (`skills/finishing-a-development-branch/SKILL.md` steps 4-5, `bin/gauntlet-telemetry-seal.mjs`).
- `plan_check` requires every task to cite one baseline SHA and roots every `Modify:`/`Create:`/`Test:` existence check at the plan file's checkout (`extensions/lib/plan-check.ts:507-612`, `extensions/phase-tracker.ts` port); pi-cohort's isolated chain rejects a task `cwd` that differs from the shared isolation cwd (`src/runs/shared/worktree.ts:139-158`), so a wave cannot mix repositories.

Premises: supported - the gauntlet-owned `## Process state` section of the brief already carries ordered N-member `PR:`/`Pre-rework head:` pairs "home first" (`skills/gauntlet-resume/reference/brief-contract.md` Producers), so the brief can hold ordered member data without touching cohort's six headings; the runtime acts on any worktree by absolute path (`extensions/lib/checkout.ts`, `doc/configuration.md` "Process in primary, work by path") while settings and flow guards load from the session cwd's checkout only (`extensions/lib/gauntlet-settings-loader.ts:20-21`); `skills/finishing-a-development-branch/SKILL.md` is 43,039 bytes against the 50,000-byte instruction-size lint, so fan-out mechanics must live in a reference file; the five stage skills may not use `cd` or `--show-toplevel` (stage-skill lint in `scripts/ci.mjs`). Corrected - "the same spec in each repo" cannot be a byte copy: `plan_check`, the plan and ledger `**Spec:**` header, and the telemetry record key off one artifact path, so one repo is the spec's home and each companion carries a leg file at the same path. Corrected - `/skill:using-git-worktrees` takes `BRANCH` as input and derives `NAME` (`/` -> `-`, `skills/using-git-worktrees/SKILL.md:73`), so the shared value every leg receives is the branch, and the shared name follows from it. Implicit dependencies found: `bin/gauntlet-spec-index.mjs` (each repo indexes its own corpus), `using-git-worktrees`' keyed `create:` contract (applies per repo), the `gh` CLI for PR creation. Unverified, carried as an edge case: whether a given companion defines its own `## using-git-worktrees` section is a per-repo fact resolved at run time.

Privacy: this spec, its eval samples, and its docs use synthetic names only - `repo-a` (home), `repo-b` (companion), `repo-a/pkg-x` (a nested package with its own rules). Committed artifacts (spec, leg files, telemetry, PR bodies) carry the portable repo identifier, never a machine-local path.

## Design

A **leg** is one member of a run:

| Field | Value | Where it lives |
|---|---|---|
| `repo` | portable identifier: `owner/name` from `git -C <primary> remote get-url origin` with `.git` stripped, else the repo-documented name: the `repo:` value of that member's own overrides `## Issue tracker` section (the source `ticket-acceptance.md` already uses for "this repo"), else the member's primary directory basename - the resolution shape-ticket's sibling rule (`repo-audit.md:81`) cites | `### Leg: <repo>` heading, task `Leg:`, brief `legs:` `repo:`, telemetry `legs:`, PR bodies, stop messages - one spelling everywhere, compared case-insensitively |
| `primary` | the member's primary checkout path: the home is the session cwd's checkout at brainstorm start; a companion is `<home PRIMARY parent>/<NAME>` from its `- sibling:` clone URL | machine-local - never committed; re-resolved from the home overrides file at handoff, resume, and finish |
| `worktree` | absolute path of the leg's worktree | machine-local - the brief's `legs:` entry and the `Worktree ready` line; re-resolved at resume from the leg's recorded `home:` pattern with `NAME` against `primary` when the brief lacks it |
| `branch` | one full `BRANCH` string, identical in every leg | `### Leg:` `branch:`, the leg file's `**Home:**` header |
| `name` | `NAME` derived from `BRANCH` by `/skill:using-git-worktrees`' existing rule (`/` -> `-`), identical in every leg | the `<name>` token of every leg's contract |
| `Rules:` | rule files from the touched-path walk, repo-relative | `### Leg:` block, task `Rules:` line |

**Eligibility and activation.** The home overrides file's `## shape-ticket` `- sibling:` lines are the eligible companion set, not automatic membership. A run is coordinated only when the ask or the ticket explicitly selects at least one declared companion: the ask names the companion's `repo` identifier, its `NAME`, or its clone URL, or the ticket carries a repo-group heading (`### <repo>`, shape-ticket's grounded-sibling form) matching a declared sibling. Each `- sibling:` value is parsed with shape-ticket's shared parser (`repo-audit.md`): `NAME` is the URL's last path segment with `.git` stripped, `IDENTITY` its normalized `host/path`, and the companion's primary is `PATH` = `<home PRIMARY parent>/<NAME>`. Matching is case-insensitive on `owner/name` against `IDENTITY`'s trailing `owner/name`, then on `NAME`; an ask token matching two declared siblings asks once before any worktree is created. Otherwise the run stays single-member and no sibling value is parsed or validated. The **member list** is home first, then the selected siblings in their declared order; only selected siblings are validated with the audit's classification (invalid configuration, `PATH` not found, not a checkout, no origin, unparseable origin, or wrong repo stop before creation, as does a `PATH` equal to the home primary). The member list is settled before Worktree First. An existing PR subject alone never activates coordination; a PR-subject rework is coordinated only when the ask selects companions the same way, and its menu then composes per Finishing below. A run with one member is the existing flow; every leg step below is identity there, except the two row 11 adopts: recorded-contract finish authority and the per-leg plan baseline header.

### Configuration

Reuse the overrides file's `## shape-ticket` section: its `- sibling: <clone url>` lines are the declared companion set for brainstorming, handoff, resume, and finishing as well as shape-ticket's audit, read through the same shared parser and `<PRIMARY parent>/<NAME>` resolution. No new overrides heading, no new `piGauntlet.*` key, no new table grammar.

Two layers of configuration, split by what they govern:

| Governs | Source |
|---|---|
| The flow: spec council, closure review, flow guards for the home spec, amend grants, issue tracker, response channels, the finish menu choice | the home's overrides file and `.pi/settings.json#piGauntlet` (settings already load from the session cwd) |
| One leg's checkout: worktree creation and teardown, spec and plan directories, rule files, verification commands, verify-before-ship patterns, PR body style | that leg's own primary - its overrides file (the documented lookup order: `.pi/gauntlet-overrides.md`, `gauntlet-overrides.md`, `doc/gauntlet-overrides.md`, first found) and its `.pi/settings.json` read by file and merged through the existing preset rules (`extensions/lib/gauntlet-settings.ts`), never through `gauntlet_setting`, which resolves the session cwd's checkout only |

Per-leg resolution, run once per leg at brainstorm step 2 and recorded in the leg's `### Leg:` block as `contract:` lines:

- **Create**: the leg's `## using-git-worktrees` section through `/skill:using-git-worktrees` with the caller inputs below - keyed `home:`/`create:` contract, or the legacy path's native tool or wrapper (`script/worktree create <name> <subproject>` style), or `<primary>/.worktrees/<name>`. A wrapper token other than `<name>`/`<branch>` (`<subproject>`) resolves from that leg's touched top-level directory; zero or several candidates ask once, per leg. The shared `BRANCH` is the `<branch>` value and the derived `NAME` the `<name>` value in every leg.
- **Destroy**: the leg's `## cleanup` worktree line, else its `destroy:` key, else the built-in removal when the path matches that leg's `home:`; a `subagents.worktreeTeardownHook` in the leg's `.pi/settings.json` runs as pi-cohort defines it. Never `git worktree remove` on a leg whose contract names a wrapper.
- **Spec and plan dirs**: the leg's `flowGuards.specDirs` from its own merged settings (default when absent); plan directories are derived from those spec dirs with `planDirsFor` (`extensions/lib/gauntlet-settings.ts:175`) - `planDirs` is tool output, never a settings input. The companion leg file lands at `<companion worktree>/<that leg's spec dir>/<home spec filename>` - the same filename, the leg's own directory. The plan and ledger stay home-owned under the home's plan dir.
- **Verification**: the leg's `## verification-before-completion` and `## PR gate` sections of its overrides file (the existing grammar - no new column) and its `piGauntlet.verifyBeforeShip` from its merged settings; the finish runs each leg's commands against that leg's worktree and primary, and applies that leg's verify-before-ship policy to commands targeting that leg's checkout (Finishing below).
- A companion with no overrides file and no `.pi/settings.json` takes every default, as a bare single-repo run does.

**Contract authority (invariant change).** A coordinated run uses its recorded, resolved per-leg `contract:` lines at every later stage; finish Step 6's current rule - "nothing from creation time is carried - the file is the contract" (`skills/finishing-a-development-branch/SKILL.md:383`) - no longer applies to a run whose spec carries `## Legs`. The recorded block is the single authority; the overrides file is not re-read at finish for such a run. A deliberate change to a leg's contract is made by amending the home spec's `### Leg:` block (and the companion leg file, Brainstorming amendments below) before the stage that uses it runs. A legacy spec without `## Legs` keeps the finish-time reread.

### Brainstorming

- Step 2 (Worktree First): settle the member list (Eligibility and activation), then invoke `/skill:using-git-worktrees` once per member with explicit caller inputs: `$ROOT` = that member's primary and `$BRANCH` = the shared branch. After each create, `git -C <worktree> branch --show-current` must equal `$BRANCH`; a leg whose rules produce another branch stops naming the leg and the branch read back (already-created legs stay and are listed). Then write `<companion worktree>/<leg spec dir>/<same filename>` for each companion - `**Home:** <repo> <branch> <spec path>` header, `## Problem` copied, `## Decisions` holding the home spec's shared text (Design, Errors and edge cases, and Out of scope outside `## Legs`, which binds every leg, plus any Design clause that names that leg's `repo` or a path under its scope), and the companion's `### Leg:` block verbatim - and commit it in that worktree, one commit per companion, each through `git -C`.

- Amendments (`reference/amendment-surface.md`): an amendment that changes `## Problem`, any shared Design/Errors/Out-of-scope text, or a companion's `### Leg:` block rewrites that companion's leg file in the same amendment, committed in that worktree.

### Implement engines

- Waves are leg-homogeneous: the plan-writer splits a wave that would mix legs into consecutive single-leg waves without breaking dependency order (a companion task that depends on a home task lands in a later wave).
- `/skill:subagent-driven-development`: each wave runs the existing isolation, `WAVE_BASE_SHA` capture, integration, review, and commit sequence against its wave's leg worktree - dispatch `cwd`, `git -C`, and the shared isolation cwd all follow that leg. The implementer, code-reviewer, and spec-reviewer prompts carry that leg's `Rules:` list (spec block plus task line) as files to read before acting. Commits land in the leg's worktree. The ledger's `**Spec:**` header keeps pointing at the home spec.
- `/skill:loop-implementation` and `agents/loop-implementer.md`: AC-row-to-leg coverage - each AC row is owned by the leg whose `### Leg:` scope names it (home when none does); a row that names two legs is split in the home ledger into one ledger entry per leg before the first iteration (the spec row is untouched). The seed and every iteration target one leg; the engine keeps one base SHA per leg and dispatches the loop-implementer with that leg's worktree as `cwd`, base, and `git -C`, plus the leg's `Rules:` list and `Leg:` as inputs. A companion iteration makes two commits: the code commit in the companion worktree, then the home-ledger update in the home worktree recording the companion commit SHA. An interrupted return (code committed, ledger not) is detected on resume by the companion head not being recorded in the ledger; the engine re-records it before the next iteration rather than re-running the row. Coordinated ownership grammar: each `### Leg:` block has exactly one `scope:` line, either `scope: none` or a comma-separated list `scope: AC 1, AC 3` using one-based original AC numbers; reject duplicate, malformed and nonexistent numbers. List a shared AC in each owning leg; an AC absent from all lists defaults home. Describe owned paths in the leg's `design:` text rather than parsing prose for ownership. Coordinated ledger grammar: retain the four-column `row | status | attempts | evidence` table and numeric entry IDs; assign IDs in original AC order, then leg membership order for an AC shared by legs. Add `## Leg mapping` with columns `row | ac | leg` naming each entry's original one-based AC number and portable repo ID exactly once. Keep `base:` as the home base; add one `base <repo>: <sha>` and `seeded <repo>: no` header per member. Set a leg's seeded value to `yes` only after a validated seed of that leg's non-cut entries; seed dispatches never change attempts. Compute initial coordinated cap as non-cut entry count times `maxIterationsPerRow` plus one seed dispatch per leg with non-cut entries (all-cut cap remains 1); retain the existing iteration, attempt, cut, funding and cap-preservation rules thereafter. Before a companion dispatch, persist `pending: <row number or seed> | <repo> | <pre-dispatch HEAD>` in the home ledger; the attributed companion commit records target, consumed iteration and bounded result evidence in its message. After validating that commit, the parent updates only that leg's seeded state or target entry, records its SHA in evidence, and removes `pending:` in the home-ledger commit. Recover an interrupted return only when exactly one new companion commit matches that pending tuple and its recorded result; unrelated movement stops. Legacy and single-member ledger bytes stay unchanged.

### Finishing

- Step 1 verification runs per leg: each leg's recorded verification set in that leg's worktree, fixes routed to the owning leg. Step 3.5 closure/conformance review runs per leg with that leg's `cwd` and the AC rows its scope owns; freshness is anchored to every audited leg head and tree, and a leg changed after its audit is re-verified and re-reviewed before its delivery. The verify-before-ship advisory loads each leg's `piGauntlet.verifyBeforeShip` from that leg's merged settings and applies it to commands targeting that leg's checkout, with a per-leg verified state - home's session-wide flag is not reused.
- Every menu row spans the run (`skills/finishing-a-development-branch/reference/legs.md` owns the mechanics, cited from the gate): PR and draft PR deliver companions first in declared order, home last (`--draft` on every create for draft); squash likewise; keep preserves every leg's worktree and branch; discard enumerates every leg's branch, commit count, and worktree path before the single typed `discard` confirmation, then tears each leg down through its recorded destroy contract. PR and draft worktrees are preserved for every leg. A coordinated PR-subject rework applies each supported menu action across its selected legs with the same disclosure and confirmation rules.
- Delivery order per PR/draft/squash: (1) for each companion in declared order - skip when its receipt validates (below), else push the branch and `gh pr create` (PR/draft) or `git -C <primary> merge --squash <branch>`, commit, and run that repo's post-squash verification (squash); write the receipt; (2) collect every companion result including skips; (3) home strip-and-seal with one `--leg` per companion; (4) home delivery. The seal never runs on a partial companion set; a seal failure stops before home delivery and after already-completed companion delivery. The plan strip happens at (3); the receipts are the restoration artifact for a retry (resume at the ship stage admits a stripped plan when every companion has a receipt).
- **Completion receipt**: one home-owned file per leg at `<home git common dir>/gauntlet/receipts/<spec filename>/<repo>` (the home primary's `.git`, resolved with `git -C <home worktree> rev-parse --path-format=absolute --git-common-dir`; never inside a worktree, so home teardown cannot remove it), written after that leg's delivery, carrying `attempted-head: <sha>`, `delivered: pr <url> <head sha> | squash <sha>`, and `verification: passed | <failure>`. A retry validates the receipt instead of inferring success: a PR receipt is valid when the open PR's head equals the attempted head (a stale PR head re-pushes); a squash receipt is valid only when `verification: passed` and the squash SHA is reachable from the primary's default branch (a failed post-squash verification re-runs the verification, not the squash); an invalid receipt makes the leg unlanded again. Default-branch ancestry of the feature head is never used as landed proof.
- A companion PR body or squash message carries `Home: <repo> <branch> <spec path>`; the home PR body lists every companion PR URL; the home squash message lists every companion SHA.
- Any leg failure stops the loop and prints `Shipped: <repo> <sha|pr> ...` and `Not shipped: <repo> ...`; the human re-runs the finish from the brief, including from a fresh session. No rollback.
- Telemetry: the home record gains `legs:` - a list of `{ repo, sha }` or `{ repo, pr }` entries written at seal; the seal bin accepts `--leg <repo>=<sha|pr-url>` repeated and rejects an entry without both parts. On retry, an existing seal is reused only when its `legs:` set equals the collected companion set; a sealed record that differs stops naming the difference. Companion repos get no record and their `.pi/gauntlet/telemetry/` is never written.
- Cleanup (step 6) removes every leg's worktree through that leg's recorded destroy contract (`## cleanup` line, `destroy:` key, teardown hook, or built-in), run from that leg's primary; a refusal is that leg's `failed` line and the tree is left as found. Cleanup runs companions in declared order, then home; after a squash delivery a failed companion cleanup skips home's cleanup, so the home tree and its receipts survive for the retry, while discard tears down every member regardless. Receipts are deleted only after home delivery and every required cleanup complete, and the report says so in one line.

## Errors and edge cases

- A selected `- sibling:` line that fails the shared parser, or whose `PATH` is not found, not a checkout, has no or an unparseable origin, names a different repo than the URL, or resolves to the home primary: brainstorming stops naming the line before any worktree is created. An unselected sibling is never resolved: a run maps each `### Leg:` identifier to a declared sibling by comparing the identifier's trailing `name` with the sibling's `NAME` (case-insensitive) before any filesystem or git probe, probes only the matching sibling, and probes the remaining declared siblings only when no `NAME` matches that identifier.
- An ask token matching two declared siblings: ask once before creation; never guess.
- A companion's clean-base check fails (dirty primary): `using-git-worktrees`' ask fires for that leg; a decline aborts leg creation; already-created legs stay and are listed for the human to remove - nothing is auto-removed.
- The shared name or branch already exists as a worktree or branch in a companion: stop naming the repo and the name; no suffixing.
- A leg's contract produces a branch other than `$BRANCH` (a wrapper that prefixes `<handle>/`): stop naming the leg and the branch read back; the invariant is one branch string in every leg, and resume check 3b compares against that same string.
- The session already sits in a linked worktree at brainstorm start: that tree is never reused as a leg; each member's create is rooted in its own primary.
- A wrapper token (`<subproject>`) with zero or several candidates in a leg: ask once for that leg; never guess.
- A leg whose touched directories are unknown at gather time: `Rules: root only - paths unresolved`; the plan-writer's re-walk fills the task `Rules:` line.
- A rule-file link that does not resolve inside the leg: `Rules: missing: <path>`, never read from memory; a link inside a linked document is not followed.
- A leg file whose `**Home:**` tuple disagrees with the home spec: resume check 3b stops naming both.
- A brief `legs:` membership that differs from the home spec's `### Leg:` order: resume check 3b stops naming the leg.
- A companion worktree whose git common dir is not its declared primary's: resume check 3b stops naming the leg.
- A task `Leg:` naming a repo absent from `## Legs`: `plan_check` FAIL `leg-unknown`; the plan is repaired, never the spec. Two legs' baselines differ: PASS (per-leg equality); a task citing another leg's SHA: FAIL.
- A wave mixing legs: the plan-writer splits it; `plan_check` fails a mixed wave.
- A loop iteration with code committed in the companion but no ledger update: resume re-records the companion head; the row is not re-run.
- Resume from a companion's primary: check 3 stops with the home named; resume from the home with a companion worktree missing (no receipt) or on another branch: check 3b stops naming the leg; per-leg HEAD/dirty drift: announced, never a stop.
- Handoff after a human removed a companion worktree: `worktree: missing` in `legs:`; resume stops on it at 3b unless a valid receipt exists.
- Ship fan-out failure (push, `gh pr create`, squash conflict, or a leg's verification): the loop stops; report lists shipped and unshipped legs; re-run from the brief validates receipts and skips proven legs; no rollback.
- A stale PR head (receipt head differs from the open PR's head): re-push, not a skip. A squash whose post-commit verification failed: the leg is unlanded; the verification re-runs on retry.
- Seal failure or a malformed `--leg` value: the bin exits non-zero naming the value; the finish stops before home delivery; delivered companions keep their receipts.
- An existing seal whose `legs:` set differs from the collected companions on retry: stop naming the difference.
- Discard on a coordinated run: the confirmation lists every leg; a single leg's teardown refusal leaves that tree and continues to the next leg's report line.
- Single-member run: `## Legs` has one block, no leg files, no `legs:` brief block, no `--leg` seal arguments, no companion loop, no receipts; a legacy spec with no `## Legs` is home-only and keeps the finish-time overrides reread.
