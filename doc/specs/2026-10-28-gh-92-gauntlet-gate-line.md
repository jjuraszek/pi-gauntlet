# Every gauntlet turn that waits for a reply or ends a run starts with one `gauntlet:` line

**Goal:** A program driving pi over RPC can tell, from the first line of the last assistant message it sees at settlement, whether gauntlet is waiting at a known gate (and which one), asking a free-form question, or finished - without a per-skill regex.
**Amend-grant:** every later spec amendment in this flow (corrected facts, paths, verification lines, and scope, acceptance-criteria, or public-contract edits alike) applies without asking; only a redraw (changed problem statement, component added, removed, or re-bounded) still stops for you, and the grant never stands in for a spec approval.
**Engine:** waves
**Ticket:** #92 (jjuraszek/pi-gauntlet)
**Predecessor:** none superseded. Extends `doc/specs/2026-10-21-gh-73-menu-numbering-after-lists.md` (`menu-layout.md` gains a second rule; its numbering and reply-mapping rules are untouched).

## Problem

Pi's RPC stream ends every settled run with the same `agent_settled` event: it fires once the agent goes idle after its whole run, automatic continuations included, and carries no waiting-vs-finished field. This repo already consumes it that way - `extensions/phase-tracker.ts:645` listens to `agent_settled` and has to infer a pending `plan -> implement` or `verify -> ship` edge from phase state (`README.md:48`). A driver therefore has only assistant text to classify a settled turn. Gauntlet's gate openers differ per skill: `Implementation complete. What would you like to do?` (`skills/finishing-a-development-branch/SKILL.md:178`), `Verdict: not ready - 2 blockers, 1 nit` (`skills/gatekeep-pr/reference/menus.md:31`), `1 - approve: ...` rows (`skills/brainstorming/reference/spec-finalization.md:149-153`), and lettered `A)` questions elsewhere. Terminal reports are free text per skill (`<ref>: written | closed | ...` at `skills/shape-ticket/SKILL.md:113`). No `gauntlet:` marker exists today anywhere under `skills/`, `extensions/`, or `doc/`; the only `gauntlet:` string is the `/gauntlet:<skill>` slash-command namespace in `README.md`.

Two of the ticket's premises were corrected during the brainstorm and the design follows the corrections:

- gatekeep-pr's `stuck - <reason>` turn is not terminal. `skills/gatekeep-pr/reference/post-selection-loop.md:64` renders it through `menus.md`'s `## obstacle` template, which ends with a `stop` row tagged `[recommended]` - a waiting gate. The run ends only after `stop` runs cleanup and teardown. The `stuck -` strings live in `post-selection-loop.md:45-74` (one at `decision-menu.md:49`), not in `decision-menu.md` as the ticket cites.
- `menu-layout.md` is cited only by the numbered-menu renderers (finishing, gatekeep-pr, shape-ticket, chase-bug, check-delivery, gauntlet-resume). The question-form gates (spec-finalization, amendment-surface, writing-plans, subagent-driven-development, loop-implementation, using-git-worktrees) do not cite it; finishing's Step 4 menus carry no `[recommended]` tag (`SKILL.md:176-215`).

A structured alternative exists in pi (an extension can raise a select/confirm dialog through `ctx.ui`, which reaches the driver as an `extension_ui_request`) but only an extension can emit it, not a skill; the user chose the text line.

Framing: pivoted to a first line without `picks=` - the field duplicates the numbered rows a driver already parses (`^\d+\. ` per `menu-layout.md`) and cannot encode the compound replies the skills accept (`fix minors F3, F9`, `show evidence`, `2; fund 3 fix rounds`). Reply reading is documented once per row layout, not per gate.

Human decisions recorded during the questionary (the spec is the log of decisions; the user declined a ticket repair):

- Every skill that stops for explicit human input decorates that turn. A turn that any proper reply can advance is a gate, never terminal; `done`/`stuck` is reserved for a turn after which the skill waits for nothing.
- Gates the model invents outside a skill template stay unmarked.
- Gate id = the step or section label the gate already carries in its skill.
- Enforcement is a deterministic lint in `scripts/ci.mjs` plus one eval sample per touched skill. Eval retry stays the runner's existing bounded confirmation (`eval/README.md:139`: one replay for a `regressed` cell; `eval/run.mjs:141`: one judge retry) - no change to `eval/`.
- The fix-round-cap nudge lives in the extension (`extensions/phase-tracker.ts`), because that is the proper home for a runtime nudge.
- Reconciliation (the spec's, not a further user answer): cut-question row 5 kept the extension nudge in scope with the ticket's `gauntlet: stuck fix-round-cap used=<N> cap=<M>` string, and the rows-1/2/6/7 answer made every turn a reply can advance a gate. The cap escalation is advanced by `grant_fix_rounds` (`conformance-check.md:186-190`), so the recoverability rule wins on the line kind: the nudge names `gauntlet: gate=verification-before-completion/step-6`, and the `used`/`cap` counts stay in the reason's existing first sentence (`extensions/phase-tracker.ts:251-252`) rather than on the marker line.

## Design

### The first-line rule (owner: `skills/brainstorming/reference/menu-layout.md`)

A skill-owned turn that ends the model's turn starts, at column 0 of the whole assistant message, with exactly one of:

| Kind | Line | When |
|---|---|---|
| gate | `gauntlet: gate=<skill>/<id>( recommended=<token>)?` | the turn renders a template listed in the contract table and waits for a reply; `recommended=` is present only when a rendered row carries `[recommended]`, and its token is that row's number; it is omitted for item-and-letter menus whose recommendation is a per-item `Recommended: <letter>` line (`amendment-surface.md:114-137`, `disposition-protocol.md:14-31`) |
| question | `gauntlet: question` | the turn asks one questionary-format question (`A)` options, `Recommendation:` line) or a yes/no-style ask a skill names, and waits |
| done | `gauntlet: done <outcome>` | the skill's terminal report: nothing is awaited, no reply advances it |
| stuck | `gauntlet: stuck <reason>` | the skill ends without its outcome and no reply advances it |

`<skill>` and `<id>` are tokens over `[A-Za-z0-9.-]+`; `<skill>` is the owning skill's directory name under `skills/` (a reference file uses its skill's name, never its own), and `<id>` is the gate's own step or section label in kebab-case (`step-4`, `user-review-gate`, `obstacle`, `verdict-menu`). `<outcome>` is comma-separated tokens with no spaces, each a bare token or `key=value` over the same charset (the charset clause of acceptance row 3 read as written); `<reason>` is free text to end of line. The marker is lowercase, never preceded by `/` (the slash-command namespace `/gauntlet:<skill>` is unrelated). The marker precedes every piece of skill-mandated prose in the message (brainstorming ### 3's premise correction and `The framing holds: ...` sentence, `SKILL.md:108-113`, come after it); the test is the first line of the whole assistant message, not of the template block. Everything after the first line is the existing template text, unchanged. The rule block states the terminal test in one sentence: a turn that any proper reply can advance is a gate or question, never `done`/`stuck`.

Settlement boundary: the line classifies the last user-facing assistant message at settlement. A report that an automatic continuation immediately follows with another skill's work in the same run (verification's `## Closure / conformance` block before `/skill:finishing-a-development-branch` is invoked, `loop-implementation/SKILL.md ## After the loop` steps 4-5, `subagent-driven-development/SKILL.md ## Continuous Execution`) is intermediate and carries no line; the gate finishing then renders is the marked turn. Ordinary answers outside a skill-owned turn carry no line. Precedence when one message carries both a report and a gate (gatekeep-pr's batch summary followed by each child's menu; finishing's closure digest followed by Step 4): the parent-rendered template's line, once - `gauntlet: gate=gatekeep-pr/batch-summary` for a batch round, `gauntlet: gate=finishing-a-development-branch/step-4` for the digest plus options.

### Lint (`scripts/gate-contract-lint.mjs`, called from `scripts/ci.mjs`)

Parses the Gates and Terminals tables of `doc/gate-contract.md` and fails `npm test` with one line per defect. It validates every inventoried render site; it cannot detect a gate the table omits.

- `gate <skill>/<id> not found at <file> <site>` - slice the rendering file from the `site` heading to the next heading of the same or higher level; for a `gate` row require its literal `gauntlet: gate=<skill>/<id>` and for a `question` row the literal `gauntlet: question`, either as the first non-blank line of a fenced block inside the slice or inside a backticked span in a sentence that starts `Start the message with` inside the slice. A row for a site with several fenced templates (`finishing-a-development-branch/step-4`: three variants) carries a `templates=<N>` note in its layout column; the lint requires exactly N fenced blocks in the slice that start with the literal. Two `gate` rows may not share one `<file> <site>` pair; `question` rows may share a site, since their literal is not keyed by id (writing-plans' three step-6 rows under `## Author the plan` and loop-implementation's two rows under `## Human stop` each share one site and one `Start the message with` sentence). Headings inside fenced blocks are not headings for slicing.
- `terminal <skill>/<ending> not found at <file> <site>` - a Terminals row whose `gauntlet: done <token>` / `gauntlet: stuck` literal is absent from its report-site slice under the same fenced-or-sentence rule.
- `<file>:<line> gauntlet: <kind> not in doc/gate-contract.md` - a `gauntlet: gate=` / `done` / `stuck` literal under `skills/**/*.md` outside every inventoried slice. `gauntlet: question` is not keyed by id and is exempt from this reverse check.
- `<file>: no resolving menu-layout citation` - a rendering file in the Gates table that lacks a relative link to `skills/brainstorming/reference/menu-layout.md` that resolves from that file.
- `doc/gate-contract.md not linked from <README.md|AGENTS.md>`.

## Errors and edge cases

- Two gates in one message (batch summary + child menu; closure digest + Step 4): one line, the parent-rendered template's.
- A nested skill's ask (using-git-worktrees' dirty-base or detached-HEAD question under brainstorming) carries its own id, not the caller's.
- A terminal report directly followed by another skill's gate in the same flow (finishing's report, then `/skill:release`'s level pick): the report turn says `done`; the next turn is the next skill's gate. An automatic handoff with no human turn between (verify -> finishing) carries no `done`; see Settlement boundary.
- `recommended=` is omitted where no row is tagged (finishing Step 4 today) and on item-letter menus; adding a tag later changes only the template, not the table.
- Resume: `gauntlet-handoff`'s brief already names the pending gate; the resumed turn's first line is that gate's id. No brief field is added.
- Shape-ticket: a run whose last turn is a `hard-stop` ask ends with that question line and no batch line; `stopped` is counted only when the run ends after that ask without values (the human moved to the next ticket or the batch finished). An all-stopped batch that finishes emits `done stopped=<N>`.
- gatekeep-pr's obstacle body may quote the extension's nudge sentence (`stuck - phase-tracker fix-round guard: <its reason>`); the message's first line stays `gauntlet: gate=gatekeep-pr/obstacle` and the quoted sentence is body text.
- The lint's position check runs only inside inventoried slices; a prose sentence in `menu-layout.md` that quotes `gauntlet: gate=<skill>/<id>` with angle-bracket placeholders does not match the literal regex (placeholders are outside the charset) and is skipped.
