# gatekeep-pr: viewer-relative pending checks from `mergeStateStatus`

**Goal:** Stop `/skill:gatekeep-pr` from withholding `merge` and recommending `wait` on a pending check or review requirement that does not bind the gating actor, by reading GitHub's own viewer-relative `mergeStateStatus` - re-read before every menu - instead of modeling rulesets, bypass actors, or team membership; zero consumer configuration.
**Amend-grant:** every later spec amendment in this flow (corrected facts, paths, verification lines, and scope, acceptance-criteria, or public-contract edits alike) applies without asking; only a redraw (changed problem statement, component added, removed, or re-bounded) still stops for you, and the grant never stands in for a spec approval.

No ticket. Amends (does not supersede) `doc/specs/2026-10-02-gh-57-gatekeep-pr-production-gate.md` (digest `permissions` block, `verification evidence pending` and CI check overlays, `wait` course) and `doc/specs/2026-09-06-gh-14-gatekeep-ci-evidence-default.md` (Evidence resolution table, CI-sufficient predicate); both stay live for every clause this spec does not name.

## Problem

A consumer repo (observed: a private monorepo on 2026-10-06) enforces a ruleset "require one approving review and the `<approval>` commit status" on `main` with bypass actors `OrganizationAdmin` and a team, `bypass_mode: exempt`. A workflow posts the `<approval>` StatusContext as `pending` on every PR until a listed approver reviews; the job itself succeeds. For an exempt viewer gating someone else's PR with green CI, the gate today:

- puts that status in the resolved check set (`skills/gatekeep-pr/verification-brief.md` Section B, "Resolved check set = ... else all checks on the assessed `headRefOid`") and maps StatusContext `PENDING` to pending;
- resolves the Evidence table's Pending row ("never an evidence-less merge"), so `source: pending` and the `verification evidence pending` overlay withhold `merge` and recommend `wait` (`reference/decision-menu.md` Overlays);
- treats the check as a pending required check in `reference/findings.md` `## Dispositions` ("merge waits until it turns green") and `reference/post-selection-loop.md` `### Merge preconditions` ("no pending required check"), with no override row (`merge anyway` lifts only the pending-reviewer and impossible-AC overlays);
- gathers `reviewDecision` (`REVIEW_REQUIRED`) but consumes it nowhere, so the model glosses the pending status plus the review decision as "another developer's approval is required" - a sentence the skill never contains.

Nothing under `skills/gatekeep-pr/` reads rulesets, bypass actors, or membership, and the ruleset endpoint (`GET repos/{owner}/{repo}/rules/branches/{branch}`) is not viewer-filtered - it lists the rules for the exempt viewer too - so parsing it would not answer "does this bind me" without further membership reads that need scopes the viewer may lack.

The digest already carries the answer: `mergeStateStatus` from the fixed Section A `gh pr view` call is computed by GitHub for the viewer's standing. Observed on the same repo from the exempt viewer: an open PR with `reviewDecision: REVIEW_REQUIRED` reads `UNSTABLE`, a draft reads `CLEAN`, and freshly pushed PRs read `UNKNOWN` while GitHub computes; none reads `BLOCKED`. The field today is read once and consumed only for `BEHIND` at the merge precondition.

Framing: pivoted to trusting `mergeStateStatus` as the viewer-standing signal - the forge already computes whether a rule binds this viewer across every rule source (classic protection, repo and org rulesets) with the right scopes; a non-`BLOCKED` value never approves a merge, it only makes the `merge` row available, and `gh pr merge` stays the final authority.

## Acceptance criteria

none - no ticket

## Design

### D1. `merge_state_status` becomes a first-class digest field, refreshed before every menu

`verification-brief.md` Section A: `permissions.merge_state_status` is set from a `gh pr view <N> --json ...` invocation that names `mergeStateStatus` - the fixed Section A call, the step-2 re-poll, the pre-menu refresh below, the compare-and-swap refetch, the wait-course and fix-wave polls. Permitted reads are exactly those `gh pr view` invocations; an ad hoc GraphQL query, `gh pr list`, or any reply carrying `errors` never updates the field (a malformed list query was observed returning `BLOCKED` for PRs `gh pr view` reports `UNSTABLE`). The schema comment on the `permissions` block names the values the gate distinguishes: `BLOCKED`, `BEHIND`, `UNKNOWN`, `unreadable` (null or unreadable), and "any other value" (`CLEAN`, `UNSTABLE`, `HAS_HOOKS`, `DIRTY`). GitHub's schema documents `BLOCKED` only as "the merge is blocked" with no per-viewer attribution; that the field is computed for the viewer's standing is this spec's observation (an exempt viewer reads `UNSTABLE` on a review-required PR), not a documented guarantee - the gate therefore never attributes a `BLOCKED` to a specific rule.

`verification-brief.md` Section A, `status_checks[]`: each entry gains `kind: check_run | status_context | unreadable` from the rollup entry's `__typename` (`CheckRun` / `StatusContext`); the fixed `gh pr view` call already returns it. `unreadable` fails closed in D2.

`reference/assessment.md` `## Provision the worktree`: the existing single re-poll after provisioning (`gh pr view --json mergeable`) becomes `--json mergeable,mergeStateStatus`; it fires when either is `UNKNOWN`. Still `UNKNOWN` after the re-poll is handled per D2 (fail-closed), never as "not bound".

**Pre-menu refresh** - a new `### Pre-menu refresh` section in `reference/post-selection-loop.md` (the file's sections are all `###`), named from `SKILL.md` step 5 (its `Read now` cell, ahead of `reference/findings.md`) and from every re-entry sentence, so it runs before the report and the menu render from one state (the first pass included - a 15-minute local run or review can stale the gather, and a report rendered before the refresh could carry a verdict the menu contradicts): run `gh pr view <N> --json headRefOid,state,mergeable,mergeStateStatus,reviewDecision,statusCheckRollup` and `gh run list -R <owner>/<repo> -c <headRefOid> --json databaseId,status,conclusion,workflowName,url`. Head moved -> the head-move rule (re-enter step 3). Head unchanged but `state` or `mergeable` changed -> route through `### Compare-and-swap` re-assessment. Head, `state`, and `mergeable` unchanged -> replace `permissions.merge_state_status`, `pr.reviewDecision`, `status_checks[]`, and `actions_runs[]` in the digest, re-normalize and re-classify per D2, re-resolve the Evidence table on the fresh set; when that re-resolve moves `source: pending` to CI-sufficient, dispatch the claim-check-only Section B helper (the wait course's existing rule) before rendering; a `gh` failure keeps the prior values and renders the `merge state` overlay through resolver reason 2 (locator `merge state not refreshed (<reason>)`, reason text `merge state unknown`). The refresh is read-only and never mints `C#` rows - comment reconciliation stays in `### Re-render`.

`reference/post-selection-loop.md`:

- `### Compare-and-swap`: the refetch list `headRefOid`, `state`, `mergeable` gains `mergeStateStatus`. A change in `mergeStateStatus` alone (head unchanged) invalidates a `merge` or `merge anyway` pick and re-enters step 5 through the pre-menu refresh (not step 3); `reply`, `review`, `approve`, and `propose ticket change` proceed, the next menu rendering from the refreshed value.
- `### Re-render`: step 1 adds the pre-menu refresh calls above (step 1 today holds only the comment and reviewer-run reads); the own-push and head-move sequences both run it as that step 1 - first read of the last pass before the menu.
- `### Wait course`: the per-iteration `gh pr view` adds `mergeStateStatus`; the loop continues while any binding pending check remains **or** `merge_state_status` is `BLOCKED`, `UNKNOWN`, or `unreadable`, until the deadline - so a state-only withhold (green CI, `BLOCKED`) actually waits for the flip instead of exiting on the first iteration; the post-wait re-fetch is the pre-menu refresh.

`reference/fix-wave.md` `## Evidence after push`: the poll's `gh pr view` adds `mergeStateStatus`; the pushed head's set is classified per D2 before the Evidence table, and the sequence runs the pre-menu refresh as `### Re-render` step 1.

### D2. Binding classification of pending checks (Section B normalization)

`verification-brief.md` Section B, Conclusion semantics, after the pending mapping: every pending check in the resolved set is classified `binding` or `not binding`, once, at normalization:

- `binding` when `merge_state_status` is `BLOCKED`, `UNKNOWN` (after the D1 re-poll), or `unreadable`; or when `kind` is `unreadable`; or when `kind` is `check_run` and its `actions_runs[]` entry (matched by the run id parsed from its `detailsUrl`, as the Held run row already does) has `status` other than `completed` - `queued`, `in_progress`, `waiting`, `requested`, `pending`, or unreadable - or has no matching entry (an external CheckRun app, or an unparsable `detailsUrl` - fail-closed: no completed-run evidence exists).
- `not binding` otherwise: a pending `status_context`, or a pending `check_run` whose matched Actions run is `completed`, while `merge_state_status` is any other value.

Trade-off, stated: a pending commit status posted by an external CI (Buildkite, Jenkins, CircleCI) is a `status_context` with no run linkage, so for a viewer it does not bind it is not waited for - the digest cannot tell it from the approval status that motivated this change. A consumer whose external CI matters makes it a required check, which binds through `BLOCKED`.

Consumers read "pending" as "pending and binding":

- Evidence resolution table, Pending row: trigger ">=1 **binding** pending check, no blocking conclusion, ...". CI-sufficient predicate: ">=1 completed `success`, zero blocking conclusions, zero **binding** pending checks, no opt-out". The Fallback row's "only inert / fail-safe conclusions" gains "or only not-binding pending checks" - a head whose only pending check is not binding and that has no `success` still falls back to the local run rather than resolving CI-sufficient.
- The Held run row is unchanged: an `action_required` run is pending by its own rule, not this one.
- `reference/findings.md` `## Dispositions`: "A pending required check mints nothing and is not dispositionable: merge waits until it turns green" becomes "A **binding** pending check (`verification-brief.md` Section B, binding classification) mints nothing and is not dispositionable: merge waits until it turns green, or `merge_state_status` leaves `BLOCKED`, or it converts to a failing check with its own `P#`. A not-binding pending check withholds nothing, never renders under `PR comments`, and prints under `show evidence` only, as `<name> pending - not binding this viewer (merge_state_status <value>)`." The `required` field stays gathered; it no longer withholds on its own - a required check that does not bind the viewer is exactly the exempt case.
- `reference/post-selection-loop.md` `### Merge preconditions`: "no undispositioned failing check in the resolved set, no **binding** pending check"; plus a new precondition "`merge_state_status` is not `BLOCKED`, `UNKNOWN`, or `unreadable`, and the pre-menu refresh succeeded". The existing "`merge_state_status` is not `BEHIND`" line stays.
- `reference/decision-menu.md`, **withhold reason resolver** - one new paragraph above `## Overlays`, the single source for the merge-withhold reason, the `PR comments` line, and the `Not offered: merge (...)` text, in this precedence: (1) `merge_state_status` `BLOCKED` -> `GitHub reports this actor's merge as blocked, so merge waits. (merge_state_status BLOCKED; reviewDecision <value>)`, `Not offered: merge (blocked by GitHub)` - `reviewDecision` rides as a locator only, never as a claim about which rule blocks; (2) `UNKNOWN`/`unreadable`, or a failed refresh -> `GitHub has not reported this actor's merge state, so merge waits. (merge_state_status <value>)`, `Not offered: merge (merge state unknown)`; (3) a binding pending check -> `A check that binds this actor is still pending, so merge waits. (<check name>)`, `Not offered: merge (<check name> pending)`. Overlays above `merge state` (merged or closed PR, draft PR, held run) keep their own reasons; the `verification evidence pending` overlay fires on the same binding pending check as resolver reason 3 and renders reason 3's text, never a `verification evidence pending` reason of its own; under two firing overlays the higher one owns the reason and the single `PR comments` line. `report.md`'s `fixable - <withhold reason>` list drops `verification evidence pending` in favor of these three reasons, and the D6 pins carry them; the old `required check pending` reason and the `A required check is still pending` template line are removed from `report.md` `## Order` and its templates.
- `reference/decision-menu.md`, new **`merge state` overlay** directly below `held run` and above `verification evidence pending`: trigger `merge_state_status` is `BLOCKED`, `UNKNOWN`, or `unreadable`, or the pre-menu refresh failed - independent of any pending check, so a green-CI state-only block (the ordinary bound-viewer review case, `CHANGES_REQUESTED` included) fires it; effect: one `PR comments` line from the resolver, `wait` as row 1, `merge` omitted with the resolver's reason, no `anyway` row; `[recommended]` goes to `approve` when the consent row renders it (someone else's PR, resolver reason 1, `reviewDecision` `REVIEW_REQUIRED`) - recommending a row attributes nothing to a rule - else to `wait` when `Blockers` is empty. The consent-table withhold sentence names it after `approve workflow run` and before `verification evidence pending`. The CI check overlay's pending clause becomes the binding-pending-check clause (resolver reason 3) with the same mechanics; under both overlays the higher one (`merge state`) owns the reason.
- `reference/decision-menu.md` `## Verbs`, `wait`: polls "every **binding** pending check in the resolved set (required or not)" and `mergeStateStatus` while it is `BLOCKED`/`UNKNOWN`/`unreadable`.
- `SKILL.md` step 5 names the pre-menu refresh in its `Read now` cell; red flag "A local verification run while CI is pending" becomes "A local verification run while a binding check is pending"; red flag "Merging around an undispositioned failing check or a pending required check" becomes "... or a binding pending check, or a `BLOCKED`/`UNKNOWN`/`unreadable` merge state"; new red flags "A menu rendered without the pre-menu refresh - owner: `reference/post-selection-loop.md` `### Pre-menu refresh`" and "Reading `mergeStateStatus` from anything but a `gh pr view` invocation, attributing a `BLOCKED` to a named rule, or treating a non-`BLOCKED` value as a merge verdict - owner: `verification-brief.md` Section A".

A non-`BLOCKED` value is never a verdict: every other merge precondition (blockers, evidence, dispositions, provenance, `mergeable == MERGEABLE`, not `BEHIND`, clean synced worktree, compare-and-swap) binds unchanged, and a `gh pr merge` refusal is reported verbatim as today.

### D3. Consent table and approval wording unchanged

The consent table (`decision-menu.md`), the "approve (never your own)" rule, `[recommended]` on `approve` for someone else's mergeable PR, and the self-approval red flag are untouched. No rendered sentence claims that another developer's approval is required: under `BLOCKED` the resolver says GitHub reports the merge as blocked and cites `reviewDecision` as a locator; on a non-`BLOCKED` someone-else PR the `approve` row renders as today and `merge` follows the preconditions.

### D4. No configuration

No `## PR gate` key is added; `reference/assessment.md` `## Configuration`, `doc/configuration.md`, and README's `## PR gate` key block are unchanged. README's `gatekeep-pr` sentence in the skills list gains one clause after "green checks on the exact assessed head count as evidence": "a pending commit status that GitHub does not report as blocking the gating actor (`mergeStateStatus` not `BLOCKED`) is not waited for - external-CI commit statuses included - while a running Actions check, an unknown merge state, and every other merge precondition still withhold".

## Errors and edge cases

- `UNKNOWN` after the D1 re-poll, or `unreadable`, or a failed pre-menu refresh: fail-closed - every pending check is binding, `merge` is omitted with reason `merge state unknown` (locator `merge state not refreshed (<reason>)` on a failed refresh), `wait` re-polls it. Same shape as today's `mergeable: UNKNOWN`.
- `BLOCKED` with no pending check (a review rule, required signatures, or any rule the digest cannot name): the `merge state` overlay fires on its own; the resolver's reason 1 renders with `reviewDecision` as a locator.
- `DIRTY`/`CONFLICTING`: unchanged - `mergeable` handles it; `BEHIND`: unchanged - `update branch`.
- A pending `check_run` whose `detailsUrl` is missing or unparsable, or whose `kind` is `unreadable`: binding (fail-closed). A `status_context` never has a run and is classified by `merge_state_status` alone - including an external CI's commit status (D2 trade-off).
- A `check_run` pending with a `completed` run but a persisting pending rollup (a stale rollup) and non-`BLOCKED` state: not binding; the forge's own view rules.
- Same head, flipped classification between two menus (a run completed, an approval landed or was dismissed): the pre-menu refresh replaces `status_checks` and `actions_runs` together with `merge_state_status`, so a fresh pending CheckRun is never paired with a cached run status.
- Draft PR: the draft overlay still omits `merge`; D2 only decides evidence and the pending line.
- A fix-wave push resets the evidence per the Fix wave row; the pushed head's `mergeStateStatus` is read by the post-push poll (D1), so an approval that was dismissed by the push flips to `BLOCKED` for a bound viewer and the menu says so.
- A bound viewer for whom GitHub reports non-`BLOCKED` despite a binding rule (the unverified premise): `merge` is offered, `gh pr merge` refuses, the refusal is reported verbatim and the menu re-renders - today's path for any forge refusal.

## Open questions

- That a bound viewer reads `BLOCKED` on a review-required PR is inferred from the exempt viewer reading `UNSTABLE` on the same PR, not observed from this account and not a documented guarantee (GitHub's schema says only "the merge is blocked"); the first bound-viewer gate run confirms or refutes it, and the edge-case fallback (forge refusal reported verbatim) holds either way.
