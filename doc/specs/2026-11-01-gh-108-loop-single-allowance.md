# Loop engine: one per-row allowance, hands-free escalation, visible budget

**Goal:** Replace the loop engine's four interacting budgets (total `cap:`, hardcoded `3 + funded N` row allowance, retry-raised allowance, grant-gated escalated round) with one number - `allowance:` in the ledger header, seeded from `loopEngine.maxIterationsPerRow` or a per-run `; allowance N` reply suffix - so that a row's budget is header allowance plus one per retry, the last allowed attempt escalates automatically under option 4 and 5 alike, the approval menu shows the value, and the task tracker renders a mandatory human-readable ledger-step description with its attempts, for example `2/5: Verify loop behavior and recovery`, never a bare row number as the description.
**Amend-grant:** every later spec amendment in this flow (corrected facts, paths, verification lines, and scope, acceptance-criteria, or public-contract edits alike) applies without asking; only a redraw (changed problem statement, component added, removed, or re-bounded) still stops for you, and the grant never stands in for a spec approval.

## Problem

The loop driver (`skills/loop-implementation/SKILL.md:25-68`) carries four budgets that interact: a total `cap: (non-cut rows x maxIterationsPerRow) + 1` (24 rows at default 4 yield 97), a hardcoded standing row allowance of `3 + funded N` with spent-funding recovery `max(0, min(attempts, 3 + N) - 3)`, a `row <n> retry` decision that raises that allowance to an absolute `allowed attempts <m>`, and an escalated round that fires only with amend permission from the `**Amend-grant:**` header. The setting named "per row" sizes only the total; a default run stops every row at 3 attempts while the header promises 4. Human stops accept two separate reply grammars (`cap +N` and `fund N fix rounds`) with no combined syntax. The approval gate (`skills/brainstorming/reference/spec-finalization.md:167-198`) shows no resolved budget and has no way to set one for a run. The ledger task projection (`extensions/plan-tracker.ts:46-99`) parses each row's attempts cell and discards it, so the tracker widget shows `row 3` with no progress.

Premises checked: the four-budget description above is read from the driver; the gate's only reply token is `fund N fix rounds`; `coordinatedMetadata` (`extensions/lib/plan-check.ts:1208-1210`) requires exactly one `cap:` header for coordinated ledgers while single-repo `checkLedger` enforces none - this contradicts ticket AC1's "without a schema change" for coordinated runs and is resolved by the Design clause "Coordinated header validator"; task names are identity in refresh (`extensions/plan-tracker.ts:194`, regex `^row \d+(?: \(\S+\))?$`), telemetry reopen counting (`extensions/lib/telemetry-collect.ts:74-76`) and resume reconstruction (`skills/gauntlet-resume/reference/reconstruction.md:106`); `plan_tracker` tasks are `{ name, status }` (`extensions/plan-tracker.ts:18`). No premise is unverified. Implicit dependencies: none missing - the driver, coordinated reference, settings resolver, plan-check, tracker, telemetry, resume reconstruction and the three eval targets (`eval/loop-implementation`, `eval/brainstorming`, `eval/gauntlet-resume`) were all found.

Framing: kept - checked the driver's budget rules, the coordinated `cap` validator, the tracker projection and refresh regex, telemetry name identity, the gate menu grammar, and the scout's objection that dropping the total cap unbounds seed, interrupted dispatches and verify repair (it does not: seed misses stop for a human, interrupted dispatches stop at the discard ask, verify repair is once per flow, ordinary misses increment attempts).

Chat additions beyond the ticket, adopted as Design: the gate menu shows the resolved allowance on rows 4 and 5; `; allowance N` on reply 4 or 5 sets the value for this run only, in-session, written into the seeded ledger (no spec-header transport); the tracker shows `<attempts>/<effective allowance>: <human-readable criterion description>` through the projection-only `label` field, not the internal task name. The user's follow-up makes readable descriptions mandatory and requires targeted parallel model evals, never broad sweeps.

## Design

Approach: per-row allowance as the sole budget (approach 1 of the two presented); the alternative - one shared pool with no per-row unit - was rejected because it drains on an alternating-failure row, gives escalation no trigger, and loses the tracker denominator.

### Budget model

- The ledger header carries `allowance: <n>` directly after `iterations:` at seeding. The value is the `; allowance N` suffix from the approval reply when present, else `loopEngine.maxIterationsPerRow` resolved through `gauntlet_setting({ key: "loopEngine" })` (default 4, floor 1). The header has no `cap:` line.
- Effective allowance of row n = header allowance + the count of `row <n> retry` decision lines for that row under `## Decisions`. The driver recomputes it from ledger bytes on every dispatch decision and on resume; the `allowed attempts <m>` tail of a retry decision is audit text, never an input.
- `iterations:` stays as the dispatch counter the child commit body echoes and `pending:` keys on; it bounds nothing.
- The ordered table in "Before each dispatch" becomes: (1) no `open` or `failed` row -> After the loop; (2) an unresolved row with attempts >= effective allowance -> human stop; (3) the two stagnation stops, unchanged (last two child `loop: row ...` commits changed no file outside the ledger and no row status; two consecutive validation misses); (4) dispatch, with the escalation check below. Rule 4's total-cap stop, the funded-round allowance, spent-funding recovery, `funded round k of N`, `budget: <spent> of <N> spent`, the `cap +N` grammar and `loop: raise cap` are removed from the driver.
- Coordinated path (`skills/loop-implementation/reference/coordinated-legs.md`): its `## Entry` writes the same `allowance:` header and computes no cap; its retained-cap language in seeds, repair and resume becomes retained-allowance; per-leg seeds, mapping, pending recovery and companion admission are otherwise unchanged. The companion result-commit recipe in `agents/loop-implementer.md` reads no header and needs no change beyond wording that mentions cap.

### Escalation, hands free

- Before dispatching row n at rule 4, when attempts == effective allowance - 1 and no `row <n> escalated` decision exists for that row, resolve `gauntlet_setting({ key: "escalationLoop" })`. Resolved `implModel` means the non-empty string the tool returns - including its existing fallback to the main-loop model when `escalationLoop.implModel` is unset or malformed (`extensions/lib/gauntlet-settings.ts:115-117`, `resolveEscalationLoop`), so under default settings the escalated round runs on the main-loop model. With a resolved model: append `row <n> escalated | implModel round | allowed attempts <effective allowance>`, commit parent `loop: escalate row <n>`, print `escalated round for row <n>`, and dispatch that attempt with `model: <implModel>` set explicitly. The `**Amend-grant:**` value is not consulted.
- One escalation per row for the whole flow: the decision survives retry, `rows +N` and resume. Attempts authorized after a spent `row <n> escalated` decision run on the default model. A row with no escalation decision (a migrated row, or one that stopped because the model was unavailable) keeps the normal predicate above: after `retry <n>` or `rows +N` raises its effective allowance, its new last allowed attempt escalates when `implModel` resolves. The parent escalate commit starts no stagnation window.
- With the settings tool unavailable or `implModel` undefined (no configured model and no main-loop model), write no decision and dispatch nothing: stop for a human before the last attempt with `Problem:` naming `escalationLoop.implModel` as the missing capability; the row's attempts stay at effective allowance - 1. `doc/configuration.md` states the main-loop fallback and that the stop is the no-main-model case only. There is no default-model last attempt.
- Exit verification (After the loop step 1) dispatches its one escalated `implementer` repair under option 4 and 5 alike, gated only by the once-per-flow `loop: repair verification` marker and `implModel`; the `iterations < cap` and amend-permission conditions are removed. A second failure stops with the verify menu.
- Amend permission from `**Amend-grant:**` keeps exactly its amendment meaning (option 5 auto-applies amends; option 4 stops); its budget token is ignored by the loop driver. `skills/brainstorming/reference/amendment-surface.md` states the budget value applies to the waves engine only and its ledger-aftermath wording preserves `allowance:` in place of `cap:`.

### Human stop

- Every implement-phase human stop - rule 2 allowance, rule 3 stagnation, missing-model, dirty-tree, commit-boundary, interrupted-dispatch and the exit-verification stop in After the loop - prints `row <n>: <attempts> of <effective allowance>` for every open or failed row, then `Preserve every row's attempts.` (replacing today's `Preserve every row's attempts and the total iteration cap.`).
- Row stops (rule 2, rule 3 and the missing-model stop) render `Stopped on row <n> (<row text>)`, the row list above, `Problem:` as today, and the offers: `retry <n> | <hint>` (appends `row <n> retry | <hint> | allowed attempts <effective allowance + 1>`, commits `loop: retry row <n>`), `rows +N` (parses anchored `rows +<n>` with `[1-9][0-9]*` and a token boundary; appends `rows +<n> | <words>` under `## Decisions`, raises the header allowance by N, commits parent `loop: raise allowance`, leaves every attempts cell and `iterations:` unchanged), Amend (amendment surface, as today), Stop. `retry` and `rows +N` are the only budget actions and appear only on row stops. Malformed `rows +0`, `rows +x`, `rows -1`: print the accepted forms once; a second invalid reply holds the stop with no commit.
- Dirty-tree and commit-boundary stops keep discard authorization only, as today; the exit-verification stop keeps amend/stop only, reached after AC5's automatic one-time repair. A budget increase never bypasses those gates.
- The model of the attempt after `retry` or `rows +N` follows the escalation predicate: default model when a `row <n> escalated` decision is already on record, otherwise the normal last-attempt escalation check. Neither action re-arms a spent escalation; only retry starts new stagnation and validation-miss windows.

### Approval gate

- Before rendering the user review gate, resolve `gauntlet_setting({ key: "loopEngine" })` once; rows 4 and 5 render the resolved value: `4 - approve, loop engine (experimental): ... allowance <n> per row` and `5 - ...: as 4 with option 2's amendment grant, allowance <n> per row`. A settings warning renders as one adjacent line; an unavailable settings tool stops, as elsewhere in the gate.
- The hint line becomes: `Add "; fund N fix rounds" (or "N more fix rounds") to 1 or 2 to fund N implement fix rounds past the escalated waves round. Add "; allowance N" to 4 or 5 to set this run's per-row allowance.`
- Reply decoding adds rows: `4; allowance 6` / `4, allowance 6` -> approve, engine loop, run allowance 6; same for 5 (with the option-2 grant). `; fund N fix rounds` on 4 or 5, and `; allowance N` on 1 or 2, re-present the gate quoting the token; malformed N (`allowance 0`, `allowance x`) re-presents the gate once quoting the token, writing nothing. The spec header persists `**Engine:** loop` and the amend grant exactly as today.
- In-session carrier: when the reply carried `; allowance N`, the approving turn prints exactly one line `run allowance: <n>` immediately before it invokes `/skill:loop-implementation`. The driver's Entry step 4 reads that line from the invoking approval turn when seeding a fresh ledger; a reply value wins over the setting, an absent line falls back to `loopEngine.maxIterationsPerRow`, and Entry prints `allowance: <n> (reply)` or `allowance: <n> (setting)` with the seeded header. The line is ignored once a ledger exists (resume uses the header only). Loss on crash before seeding stays accepted (Errors); no spec-header persistence. `doc/gate-contract.md` documents the suffix on rows 4/5, the `run allowance: <n>` line, and replaces `cap +N` with `rows +N` in the free-reply row.

## Errors and edge cases

- `; allowance N` with N outside `[1-9][0-9]*`: the gate re-asks once quoting the token; a second malformed reply holds the gate. `; fund N fix rounds` on 4/5 is re-asked the same way.
- Allowance 1: the row's only attempt is its escalated round when `implModel` resolves (under default settings, the main-loop model); with no resolvable model the missing-model stop fires before any attempt, and the human may `rows +N`, configure the model and resume, or stop.
- Escalated attempt admitted as a validation miss: attempts become saved + 1 (`loop: repair row <n>`), which reaches the effective allowance, so the row stops under rule 2 on the next pass; the `row <n> escalated` decision stays on record (spent).
- Escalated attempt returns dirty, with zero or extra commits: the boundary rejection restores the pre-dispatch target cells as today (attempts stay at effective allowance - 1), the `row <n> escalated` decision stays spent, and discard/reset authorization proceeds as today. After an authorized discard the row is still below its allowance, so the driver dispatches it again on the default model with no retry or `rows +N` needed; exhaustion is asserted only when the attempts counter reaches the allowance. No rejected dispatch increments attempts.
- Stagnation precedes escalation: two ledger-only child commits with no status change stop before the escalated round is spent, so the stronger model never runs the dead end the human has not seen.
- Crash between approval and seeding: no ledger exists, so a resumed flow enters `/skill:loop-implementation` fresh and seeds from the setting; the reply-suffix allowance is lost and the user may `rows +N` at the first stop. Accepted (in-session transport by decision).
- Legacy `**Amend-grant:** fund 3 fix rounds` on a resumed loop run: the budget token is ignored; the amend meaning (none) stands.
- `rows +N` on a coordinated ledger raises the single shared header; every leg's rows gain N.
- Tracker: a row whose effective allowance rises by `rows +N` or a retry re-renders on the next refresh; the label never appears on Gn conformance tasks.
