# The implement orchestrator holds a wave manifest, never the plan

**Goal:** During the implement phase the primary agent coordinates from a compact manifest that `plan_check` derives from the plan on every pass; implementers and reviewers read their own task from the plan file and return a structured verdict with the full report filed away, so the plan, the spec, task bodies, review reports, and worktree source files never enter the primary's context.
**Amend-grant:** every later spec amendment in this flow (corrected facts, paths, verification lines, and scope, acceptance-criteria, or public-contract edits alike) applies without asking; only a redraw (changed problem statement, component added, removed, or re-bounded) still stops for you, and the grant never stands in for a spec approval.
**Engine:** waves

## Problem

Two gauntlet runs on 2026-10-29 (a rule-bot session and a customer-ops session) grew the primary's context to 424k and 264k tokens during the implement phase. Forensics over both session logs classified every primary `read`/`bash` result above 2,000 chars by trigger: zero bytes trace to plan text (neither plan addresses the orchestrator; the customer-ops plan's one orchestrator-directed line asks it to persist a measured value into a task); 855 KB of the customer-ops session's 1.33 MB and the bulk of the rule-bot session's compaction recovery (661 KB, 453 KB of it after the user's explicit "reread the gauntlet flow" instruction) trace to the subagent-driven-development contract; the remainder (283 KB rule-bot, 170 KB customer-ops) is the primary doing worker-shaped verification on its own - in its own words, "I confused mechanical provenance checking with work the orchestrator needed to do directly" - which the same contract invites because it already has the primary reading, verifying, and running things between waves.

The contract lines that assign the bytes to the primary, all in `skills/subagent-driven-development/SKILL.md`: `:20-26` "Your context window holds the full plan ... You read the plan"; `:46` extracts `SCOPED_TEST_COMMANDS` from the plan; `:48` runs the amendment path inline with the spec in context; `:123` reads the spec's `## Legs`; `:137` (implementer), `:143` (spec-reviewer), `:258` and `:271` (the chain steps) paste `<full task text ...>` into every implementer and spec-reviewer dispatch, which is why the primary must read each task body (`:146`, the code-reviewer dispatch, carries a diff range and no task text); `:284` reads every spec-review report file for its `Verdict:` line and carries "its full contents verbatim" into re-reviews; `:355` lists "Making a subagent read the plan" as a red flag. The customer-ops plan grew from 11 to 26 tasks through 13 `plan_check` calls and 23 spec edits in one flow, and the primary re-read it in 27 distinct 300-line windows; every compaction then costs 180-450 KB because the contract says the primary holds that material.

Premises checked against the source. Supported: pi-cohort appends the inline output to the saved-file reference unless `outputMode: "file-only"` is set (`pi-cohort/src/runs/shared/single-output.ts:199-207`); under `file-only` a chain's `## Outputs` section carries each task's `structured` output next to the pointer text, and the section renders only when some chain step declares `stopOn` (`pi-cohort/src/runs/foreground/chain-execution.ts:475-488`, `src/shared/formatters.ts:77-94`); a single (non-chain) `subagent()` under `file-only` puts only the "Output saved to:" pointer in model-facing `content` and keeps `structuredOutput` in `details` (`src/runs/foreground/subagent-executor.ts:2101-2142`, `src/runs/shared/attempt-finalization.ts:284-286`), and single/`tasks` dispatches have no `outputSchema` wiring (`src/extension/schemas.ts:208-316`); `outputMode` lives on each parallel task item, not on the parallel step (`src/shared/settings.ts:112-118`, `:428`); the parser already yields per task its wave number, heading, `Files:` entries and `Tests:` bullets and per wave its label text (`extensions/lib/plan-check.ts:45-70`, `parsePlan` at `:142`, `waveRe` at `:183`), while `Task.leg` is assigned only inside `checkPlan` (`:1288-1293`), which returns findings alone and keeps the ledger discriminant internal (`:1285`); the flow guard inspects only `write`/`edit`/`bash` (`extensions/phase-tracker.ts:721-734`). Corrected: the uncapped `plan_check` FAIL reply (1,013,451 chars for 2,740 findings) never reached the model - pi-condense spilled it before the next call (`PRUNING.md:675`, `spillThreshold` default 65,536 on `resultText.length`) - so it is not a cause and is out of scope. Corrected: pi-condense's "newest read wins" supersession applies only to `protectedPaths` (default `**/skills/**/*.md`, `**/gauntlet-overrides.md`) and content-hash dedup needs byte-identical results; the 28 plan windows were pairwise distinct, so no pruner can collapse this read pattern - the contract has to change. Corrected during design: the parser has no dependency field; wave membership is the plan's dependency structure, so the manifest carries no `depends:` field. Confirmed: a tool result's `details` payload is not model-facing (pi `docs/extensions.md:248`, `:259`); the design relies on `content` only.

Framing: pivoted to the implement-phase primary contract - the user ruled brainstorming out ("the model goes wild during implementation only"), refused a read guard or any other patch over the contract, and chose a derived manifest over an authored one or a coordinator child.

## Design

### 1. `plan_check` returns the manifest

Change `checkPlan` in `extensions/lib/plan-check.ts` to return `{ findings: PlanCheckFinding[]; parsed?: ParsedPlan; ledger: boolean }` so the handler receives the same normalized plan the checks ran on: `parsed` is the `ParsedPlan` after `checkPlan` has assigned every `Task.leg` (explicit `Leg:` line or the first spec leg as default, `:1288-1293`), and `ledger` is the line-1 `# Ledger - loop engine` discriminant (`:1285`). Add `renderManifest(parsed: ParsedPlan, planAbs: string, specAbs: string): string` on that normalized plan. The rendering is line-oriented: one text header, then one JSON object per task (`JSON.stringify`, fixed key order, no wrapping, tasks in plan order):

```
manifest: <absolute plan path> | spec: <absolute spec path> | tasks: <N> | waves: <M>
{"task":4,"wave":2,"mode":"in-place","heading":"<text after \"### Task 4: \">","files":[{"kind":"Create","path":"src/x.ts"}],"tests":["npm test -- x","node scripts/y.mjs; echo done"],"leg":"jjuraszek/pi-gauntlet","orchestrator":"persist the measured value into Task 9"}
```

`files` lists every `FileEntry` as `{kind, path}` in plan order; `tests` is the array of the task's `Tests:` bullet commands, each element one command verbatim (a command containing `;` or `|` stays one element; two bullets stay two elements), or `[]` for the no-tests form; `mode` is present only when the wave heading label carries the `in-place` marker that `writing-plans` writes for a rebase-form Task 1 (`skills/writing-plans/SKILL.md:199`); `leg` is present only when `Task.leg` is set; `orchestrator` is present only when the task body carries an `Orchestrator:` line. JSON encoding is the lossless rule: a heading, path, or `orchestrator` text containing `|`, `;`, quotes, or newlines round-trips unchanged, and the primary never joins or splits commands - it executes each `tests` element as its own `(cd "<worktree>" && <command>)` with its own failure boundary, as today's scoped gate does per bullet. Add `orchestrator?: string` to `Task`: a body line matching `^Orchestrator: (.+)$` (first match wins) sets it; the grammar is added to `skills/writing-plans/reference/plan-contract.md` as an optional task line, and `plan-writer` uses it only for an instruction the orchestrator must act on between waves. Everything else in a task body is for the implementer and reviewers and is invisible to the orchestrator by design.

In the `plan_check` handler (`extensions/phase-tracker.ts`, pass branches at `:1070-1076`), on pass the `content` text becomes the existing pass line, a blank line, and the manifest; both the stamped and the `(no flow to stamp)` branch render it; the stamp logic is unchanged. Before stamping, the handler measures the complete `content` string (pass line, blank line, manifest) as a JavaScript string length; at 32,768 characters or more it takes the existing fail path with a single finding `manifest-size @ line 0: manifest content is <chars> characters (limit 32,768); the plan is too large for the orchestrator's manifest - stop and ask the user to reduce it` and sets no stamp. Rationale: pi-condense spills a tool result into a sidecar file once `resultText.length` reaches its `spillThreshold` (default 65,536 characters, configurable; `PRUNING.md:675-677`), and a spilled manifest would force the orchestrator to `read` it back - the exact pattern this spec removes; half the default leaves headroom for the pass line and for a lowered configured threshold, and a 26-task plan renders in well under 8,000 characters. The assumption that `spillThreshold` is at its default or above 32,768 is stated in `doc/configuration.md`. A ledger (`ledger: true`) returns today's text; no manifest. The FAIL path is unchanged.

Every `plan_check` caller receives the manifest on a pass - the `plan-writer` child's self-checks (`agents/plan-writer.md:5` lists `plan_check` among its tools), writing-plans' parent stamping call (step 5), and gauntlet-resume - so the plan-phase primary and the planner child each gain up to the limit per call. This cost is accepted: it is bounded by the limit, the tool has one output shape, and no instruction outside the implement phase changes because of it.

Remove: nothing in this component.
Add: `renderManifest`, the `checkPlan` result shape, `Task.orchestrator`, the `manifest-size` finding kind, the `Orchestrator:` grammar line in `plan-contract.md`.

### 2. The orchestrator's state during implement

Rewrite `skills/subagent-driven-development/SKILL.md` around the manifest. A new `## Orchestrator holds` section near the top enumerates the primary's allowed context during implement: the manifest (from `plan_check`), `plan_tracker` state, skill resources (the `read` tool at their absolute skill paths, as today), the structured status and verdict JSON from each dispatch result (section 3), the `Artifacts:` patch locations, scoped-test and git coordination command output, the `Worktree ready` values from provisioning or the resume brief, and the compact return data of delegated reads (below). It names what the primary never opens during implement: the plan file, the spec file, task bodies, implementer reports, review reports, worktree source files, and any shell command that loads file contents (`cat`, `sed -n`, `git show <path>`, `git diff` without `--stat`, `grep`/`rg` with context over source). The "Output saved to: ... Read this file if needed." pointer in every file-only result is not an instruction: the primary never follows it. Git coordination commands stay with the primary (`rev-parse`, `status --porcelain`, `diff --stat`, `apply`, `reset --soft`, `add -A`, `commit`, `update-ref`), as does the scoped test gate (step 5) and its redirected output file.

Every read the primary would otherwise do during implement is delegated. Source investigation, worker-shaped verification ("does the patch really cover X?", provenance checks), a human's question about a task's content, and the text of a human escalation about a task are each answered by a delegated read: a one-step chain dispatch (section 3 carrier) whose task names the paths and the question and whose `outputSchema` bounds the reply to `{ answer: string (one paragraph), evidence: string[] (path:line, each one line) }`; the primary holds that essence only. There is no bounded single-task read exception for the primary anywhere in implement.

Remove from the skill: `:20-26` ("Your context window holds the full plan ... You read the plan"); the `:355` red flag "Making a subagent read the plan" (replaced by its inverse: "Pasting task text, spec excerpts, or report contents into a dispatch, or opening the plan, spec, a report, or a source file in the primary"); the pasted `<full task text ...>` in the dispatch shapes at `:137`, `:143`, `:258-271` and in the repair dispatches of steps 5-6; the `:284` instruction to read each SR report for its `Verdict:` line and to carry report contents verbatim, and its session-artifact rule that recovers failed-task prose into the primary; the `:123` `## Legs` spec read; the `:46` plan read for `SCOPED_TEST_COMMANDS`; the inline-plan and inline-spec reads in the `:48` amendment route; `:48`'s "Keep the orchestrator as the spec's only writer during execution".

Add: `SCOPED_TEST_COMMANDS` is the union of the wave's manifest `tests` arrays, one element per command, and remains the parent's integrated test gate. An initial or re-dispatched implementer running in an isolated `worktree: true` checkout receives only its own task's `Tests:` commands, taken verbatim from that task's manifest `tests` array. In-place repairs and code review receive the wave's `SCOPED_TEST_COMMANDS` union because they run on the integrated tree. The wave's owned files and the independence check (step 1) read the manifest `files` fields; leg routing reads the manifest `leg` field and the leg's `Worktree ready` path already in context; an `in-place` wave is one whose manifest lines carry `"mode":"in-place"`, and the existing `:174` in-place rule (one implementer in the branch checkout, no `worktree: true`, no `reset --soft` fold) keys on that field. A task with an `orchestrator` field: the primary acts on that text once, at the boundary after the task's wave completes (after step 7's commit, before the next wave's dispatch), and only with coordination actions - a `plan_tracker` or `phase_tracker` call, a `gauntlet_setting` read, a git coordination command, carrying a value from a structured output into the next dispatch text, or starting the delegated amendment path of section 4. Text that asks the primary to change the plan or the spec (the fixture's "persist the measured value into Task 9") is executed as an amendment: the value comes from the structured output of the wave's implementer, and the edit goes through section 4; the primary never edits a source document directly. Text naming no action the primary can take this way becomes a stop note. The manifest line is the only source of the instruction.

Compaction or resume recovery inside implement is `plan_check({ planPath })` plus `plan_tracker({ action: "status" })` for the static state. The in-flight wave's dynamic state is recovered only from the primary's own transcript lines, which the skill now requires it to print as it goes: `wave <w> base <sha>` when `WAVE_BASE_SHA` is captured, `wave <w> task <n> <status|verdict> <value> report <path> patch <path>` after each result is read, `wave <w> review <k> tree <path>` for each materialized review tree, and the existing `funded round <k> of <N> for task <n>` lines (`reference/fix-loop.md:23`). A `plan_tracker` status of `in_progress` without those lines for the current wave means the primary cannot tell pre-dispatch from partially integrated from awaiting re-review; it stops with a stop note naming the wave and the missing lines instead of guessing, re-dispatching, or resetting a repair budget.

### 3. Dispatch shapes and the verdict carrier

The verdict carrier is pi-cohort's chain `## Outputs` section: it renders in model-facing `content` when some chain step declares `stopOn`, and under `outputMode: "file-only"` it carries each task's `structured` JSON next to a pointer, never the report (`chain-execution.ts:475-488`, `formatters.ts:77-94`). Every dispatch in implement therefore goes through a chain:

- The wave chain keeps its two steps. `outputMode: "file-only"`, `output:` under `REPORT_DIR`, and the persona's `outputSchema` go on every parallel task item of both steps (`ParallelStep` has no `outputMode`; an item without it defaults to `inline` and would return its whole report into `## Outputs`, `settings.ts:428`). `stopOn` stays on the implementer step only. The sentence "Give the SR step ... its tasks no `outputSchema`" is replaced.
- Every other dispatch that returns a status or verdict (initial CR, SR and CR re-reviews, repair implementers including escalated and funded rounds, the post-repair SR, the "Chain stopped or failed" SR fan-out, the spec-gap redispatch, and section 2's delegated reads) is a one-step chain: `chain: [{ parallel: [<one or more task items with agent, task, cwd, output, outputMode: "file-only", outputSchema>], stopOn: { path: "/status" or "/verdict", in: [<the non-clean values>] } }]`. With one step the stop has nothing downstream to skip; it exists so `## Outputs` (and `## Stop`) render. A single `subagent()` or `tasks:` dispatch is never used for a verdict-bearing child, because its model-facing `content` is the pointer alone and it has no `outputSchema` wiring. The one agent-less child, the failed-chain diagnosis child of section 3, is a one-step sequential chain instead (`chain: [{ task, output, outputMode: "file-only", outputSchema, stopOn }]`, no `parallel:`), because a parallel item requires `agent` (`schemas.ts` `ParallelTaskSchema`, `required: ["agent"]`) while a sequential step's `agent` is optional (`ChainItem`, `schemas.ts:206`) and sequential steps evaluate `stopOn` and log to `## Outputs` the same way (`chain-execution.ts:1225`, `:1268`). No pi-cohort change is required.

Every implementer, spec-reviewer, and code-reviewer task item carries `planPath: <absolute plan path>` and either `anchor: "### Task <n>:"` or, for a wave-wide CR or a multi-task repair, `anchors: ["### Task <n>:", "### Task <m>:"]` in its task text, plus the absolute spec path from the manifest header. The anchor is the exact heading-line prefix `### Task <n>:` (number then colon, so `### Task 4:` never matches `### Task 40:`); the child reads from that heading line to the next line matching `^#{2,3}\s` (the parser's heading boundary) and, for an anchor list, the union of those sections. The child reads its task at the anchor, its `Spec:` anchors, `Files:`, and `Tests:` block itself, and derives its Rules itself: the `Rules:` lines in its anchored task body plus the `Rules:` lines of its leg's entry in the home spec's `## Legs` (the spec path is in the dispatch; the leg is the task's `Leg:` line or, absent, the first `### Leg:` entry), applying both as the current combined list. Wave CR remains exactly one initial dispatch per code-touching wave (`:183`), now over the anchor list of the wave's tasks; a multi-task repair implementer carries the anchor list of the tasks it touches. The dispatch passes only the task's manifest `tests` commands to an initial or re-dispatched implementer running in an isolated `worktree: true` checkout; in-place repairs and code review receive the wave's `SCOPED_TEST_COMMANDS` union, which remains the parent's integrated test gate. For dependent tasks, the dispatch also passes the previous task's status line and report path instead of its summary text.

Structured output shapes (`outputSchema` on every task item; the report keeps its existing layout and the JSON mirrors the report's status/verdict line and footer):

- implementer: `{ status: DONE|DONE_WITH_CONCERNS|NEEDS_CONTEXT|BLOCKED, reasoning: string (one sentence, 300 chars), concerns?: string[] (required for DONE_WITH_CONCERNS, one line each), question?: string (required for NEEDS_CONTEXT), anchorUnreadable?: string, measured?: object (values an `orchestrator:` instruction consumes) }`.
- spec-reviewer: `{ verdict: COMPLIANT|NEEDS_REWORK|OUT_OF_SCOPE_CHANGES, reasoning: string (one sentence), maxSeverity?: PARTIAL|MISSING|SCOPE_CREEP, findingCount?: number, parallelSafe?: string (the `Parallel-safe:` line verbatim), touchedTasks?: number[], trajectory?: { verdict: CONVERGING|DIVERGING|STAGNANT, line: string (the `TRAJECTORY:` line verbatim) }, anchorUnreadable?: string }`.
- code-reviewer: `{ verdict: SHIP|FIX_FIRST|REJECT, reasoning: string (one sentence), maxSeverity?: Critical|Moderate|Minor, findingCount?: number, behaviourChange: boolean (every report, mirrors `Behaviour-change:`), parallelSafe?: string, touchedTasks?: number[], trajectory?: { verdict, line }, anchorUnreadable?: string }`.

Routing reads only these fields: the status table from `status`, `concerns`, and `question`; the fix-loop sequence from `trajectory.verdict`, `maxSeverity`, and `findingCount` (the `3 -> 1, max severity Moderate` arithmetic); the behaviour-change reroute from `behaviourChange`; fix fan-out from `parallelSafe`; funded-round owners from `touchedTasks`. Findings prose stays in the saved report and reaches the next child by path. Missing-field handling: a required field absent or a schema rejection is a failed task (pi-cohort marks it; `## Outputs` carries the error) and routes as below; an optional field absent on an issue-bearing review (`trajectory` on a re-review, `parallelSafe` on fan-out, `touchedTasks` on a multi-task repair) is treated as the conservative value today's text assigns to a missing line (no `TRAJECTORY:` line -> escalate; no `Parallel-safe:` -> serial; no touched owners -> every task in the dispatch).

A chain that errors without a matched stop renders no `## Outputs` (`chain-execution.ts:480`, `failureSummaryOptions` needs a `stopRecord`). The primary then dispatches one diagnosis child as a one-step sequential chain (`chain: [{ task, ... }]` with `agent` omitted so it inherits the main loop - optional on a sequential `ChainItem`, `schemas.ts:206`, required on a parallel item - with invocation-level `context: "fresh"` and a `stopOn: { path: "/decision", in: ["retry", "repair", "stop"] }` so `## Outputs` renders), whose task names the chain's `Artifacts:` directory, the known `output:` paths, and the session-artifact locations, and whose `outputSchema` is `{ tasks: [{ task: number, status: string, reportPath: string, patchPath?: string, diagnostic: string (one sentence) }], decision: retry|repair|stop, diagnostic: string }`. The primary routes from that JSON under "Chain stopped or failed" with the existing bounded retry and missing-artifact stop behaviour; the primary never opens a session artifact or a report itself.

Repair and re-review dispatches (steps 5-6, Fix-Loop Rounds, Chain stopped or failed) name the prior report by path under `## Previous review report (re-review trigger)` and the failing test output by its captured file path under `REPORT_DIR` (the orchestrator writes the scoped-gate output there with shell redirection instead of holding it); the trajectory block and `## Fix delta` are unchanged. The chained SR task's `acceptance` reason (`:270`, `:282`) becomes `"the parent takes each SR verdict from the chain's ## Outputs structured JSON; review trees are staged by design"`.

The SDD-local templates `implementer-prompt.md`, `spec-reviewer-prompt.md`, and `code-quality-reviewer-prompt.md` are rewritten to the same contract: they stop asking for the full task text, implementer summaries, pasted prior reports, and primary `Verdict:` or footer reads, and instead carry `planPath`, the anchor or anchor list, the spec path, the prior report path, and the structured-output requirement.

Persona edits (`agents/implementer.md`, `agents/spec-reviewer.md`, `agents/code-reviewer.md`; frontmatter byte-identical) are conditional on the SDD payload so callers outside SDD (`requesting-code-review`, verification's conformance check) keep their inline requirement blocks: "When the task carries `planPath` and `anchor`/`anchors`, read the task section there first and treat it as the task text; otherwise the task text is inline as before." An unreadable anchor yields, in both the report and the structured output, `BLOCKED` (implementer), `NEEDS_REWORK` (spec-reviewer), or `REJECT` (code-reviewer - its vocabulary stays `SHIP`/`FIX_FIRST`/`REJECT`), with `anchorUnreadable: "<path>#<anchor>"` required in that case and `Reasoning: anchor unreadable: <path>#<anchor>` in the report. The existing report layouts and verdict vocabularies stay; the structured output mirrors the report.

### 4. Amendments mid-implement

The `:48` amendment route keeps `amendment-surface.md`'s gate, grant, and `Amend-grant:` decoding semantics and its human gate; what changes, for the implement caller only, is who reads and writes. Evidence (a `plan_check` FAIL line list, an implementer's structured `concerns`/`question`, a baseline row carried in structured output) is already in the primary's context. Preparation is delegated: the primary dispatches `plan-writer` as a one-step chain with an implement-only `Amend-prepare:` block carrying the evidence; the child reads the spec and plan and returns `{ items: [{ evidence, recommended: "accept" | "alt-<n>", location: "<spec section>", edit: string (the proposed edit text, bounded to one paragraph) }], redraws: [{ location: "<spec section>", reason: string (max 300 characters) }] }`. Both `items` and `redraws` arrays are required, including when empty; redraw proposals appear only in `redraws`, never in `items`. Malformed preparation output fails. A nonempty `redraws` array holds the whole batch at the existing redraw gate before grant evaluation or applying any sibling item; the primary never opens the preparation report to discover redraws. With no redraws, the primary presents the items through the existing grant predicate and Value decoding unchanged (malformed -> stop and quote; no permission -> stop) and, on amend permission, dispatches `plan-writer` again as a one-step chain with an implement-only `Amend-apply:` block carrying the granted items verbatim. That dispatch authorizes `plan-writer` to edit the named spec sections (an extension of `agents/plan-writer.md:3`, "the plan file is its only output", scoped to the `Amend-apply:` block; outside implement the persona is plan-only as today) and then to regenerate the plan through the existing `Amend:` entry (`skills/writing-plans/SKILL.md:86`, amendment-surface section 5) with the same preservation rules (unaffected task titles and wave positions kept), run its own `plan_check` self-check, and return `{ amendedSections: string[], tasksAdded: number[], tasksAnchorChanged: number[], tasksRemoved: number[], passed: boolean, failLines?: string[] }`. Before the first apply, capture the original task numbers, titles, spec anchors, and wave positions in the existing saved apply report; retain that original inventory on every return, including failures. The primary prints `amended the spec: <title> - <location>` from the returned items, re-runs `plan_check`, takes the manifest, and reconciles the tracker from the returned numbers (`plan_tracker` `add` for `tasksAdded`; completed tasks in `tasksAnchorChanged` reopened as `in_progress`; `tasksRemoved` handled as today) without reading the plan or the spec. A `passed: false` reply with `failLines` repeats the apply dispatch once with those lines as the rule and `previousApplyReport` set to the first apply report path; the fresh retry worker reads the original inventory there, applies the granted edits idempotently without duplicating already-applied edits, and computes task deltas against that original inventory rather than the already-mutated plan. Missing original inventory fails the retry; a second failure goes to the user. Keep the one-retry budget, the apply result schema, and the existing report artifact unchanged; add no sidecar. Align the plan-writer persona, amendment surface, and Task 4 caller schemas and payloads with this contract. Add contract tests for redraw-only and mixed redraw/amend batches and for a first apply that changes task anchors then fails self-check followed by a fresh retry that returns those original anchor changes. The lines in `skills/brainstorming/reference/amendment-surface.md:180-186` that have the parent apply the edit, re-dispatch the plan-writer, and read the amended plan are rewritten for the implement caller to this contract; the planning-phase caller's lines are unchanged.

## Errors and edge cases

- `plan_check` FAIL: finding list as today, no manifest, no stamp.
- Pass with no flow active: manifest returned, no stamp (plain lint use).
- Repeated `plan_check` on an unchanged stamped plan: same hashes re-stamped, same manifest - the compaction-recovery path.
- After an amendment the hash mismatch already forces a re-run; the `Amend-apply:` child edits, the orchestrator re-checks, the new manifest replaces the old, the tracker is reconciled from the child's returned task numbers.
- Pass content at or above 32,768 characters: `manifest-size` finding instead of a manifest, no stamp; the orchestrator stops with a stop note asking the user to reduce the plan (no planner split procedure exists; none is added).
- A task body addressing the primary without the `Orchestrator:` line is invisible to the orchestrator; `plan_check` does not detect prose addressed to it.
- An `orchestrator` instruction that names no coordination action: stop note quoting the text.
- Child cannot open `planPath` at the anchor: structured `BLOCKED` / `NEEDS_REWORK` / `REJECT` with `anchorUnreadable` set; routed as a failed attempt under "When a Subagent Fails".
- Chain result without the expected structured JSON for a task (schema rejected, task failed, chain error without a matched stop): the diagnosis child of section 3 returns the compact statuses and decision; the primary opens nothing.
- A wave chain whose `## Outputs` is present but a task's `structured` is missing: that task is failed; siblings' JSON stands.
- Recovery mid-repair without the transcript lines of section 2: stop note, no re-dispatch.
- `file-only` without `output:` is rejected by pi-cohort (`single-output.ts:120-121`); every task item in the skill sets both.
- Callers outside implement (`plan-writer` self-check, writing-plans stamping, gauntlet-resume) receive the manifest too; accepted and bounded by the limit, their instructions unchanged.
- Loop engine (`/skill:loop-implementation`): untouched; its ledger path returns no manifest.
